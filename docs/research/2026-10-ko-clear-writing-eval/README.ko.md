# 한국어 기술 글쓰기: 검토 결과와 제안

2026-10-09 · [English](README.md)

**지금은 새 스킬을 추가하기보다 기존 지침에 빠진 핵심 규칙만 보완하는 것을 권합니다.**
상세 절차는 반복되는 문서·PR·핸드오프 작업에서 필요가 확인될 때 분리하고,
첨부 검사기를 필수 통과 기준으로 사용하지 않는 편이 좋겠습니다.
기존 한국어 교정 스킬은 원문 교정 역할을 유지합니다.

이번 작업은 검토와 실험, 도입 제안입니다. 제품이나 개인 설정에 설치하지 않았습니다.

## 왜, 어떻게 실험했는가

| 실험 | 이유 | 방법 | 확인한 결과 |
| --- | --- | --- | --- |
| 기존 근거 재현 | 첨부 보고서의 수치부터 신뢰할 수 있는지 확인 | 파일 57개 해시 확인 후 복사본에서 macOS Python 3.9.6으로 실행 | 키트 41개 테스트, 연구 자료의 앵커 68개·린터 기대값 24개 재현 |
| 경계 사례 검사 | 작성자가 만든 정상 예제 밖에서도 검사기가 맞는지 확인 | 별도 에이전트가 합성 사례 15개 실행 | 정상 대조군 4개, 구체 결함 8개, 숫자 문법 공백 1개, 명시된/증거상 한계 2개 |
| 실제 모델 비교 | 긴 지침이나 스킬이 실제 답변에 도움이 되는지 확인 | 합성 과제 8개 × 기본/짧은 지침/전체 지침 × 모델 3종 | 72회 시도, 답변 71개 확보·익명 채점 |

키트의 26쌍 사례는 41개 테스트에 포함됩니다. 이를 독립 시험 67개라고 합산하지 않습니다.
Grok 1건은 첫 격리 환경의 인증 실패로 생성되지 않았으며, 글쓰기 실패로 세지 않았습니다.

## 실제 모델 결과

| 실제 실행 모델 | 기본 | 짧은 지침 | 전체 지침 |
| --- | ---: | ---: | ---: |
| Codex `gpt-6-astra` high | 8/8 | 8/8 | 8/8 |
| Claude `claude-opus-5-5` | 7/8 | 6/8 | 8/8 |
| Cursor `Grok 4.7 256K High` | 8/8 | 7/7 | 8/8 |

수치는 **확보한 답변 중 사전의 근거·범위·출력 형식 기준을 통과한 답변**입니다. Opus는 high를 요청했지만
실제 effort는 영수증에 없어 확인하지 못했습니다. Grok은 실행 모델 표시명에 High가 있습니다.

Opus의 실패 중 두 건은 같은 보고 과제였습니다. 근거에는 `17 passed, 2 skipped`만 있는데
“스킵 사유는 확인하지 않았다”는 수행 이력을 덧붙였습니다. 전체 지침에서는 이 주장이
없었습니다. 사례별 1회이므로 전체 지침의 우월성을 입증한 결과는 아닙니다.

여기서 보완할 규칙은 구체적입니다.

> 사유가 제공되지 않았다는 것과, 담당자가 확인하지 않았다는 것을 구분한다.

나머지 한 건은 짧은 지침 조건의 커밋 메시지가 변경되지 않은 interval 값을 덧붙인 사례입니다.
사실 자체는 diff로 뒷받침되지만, 사전에 정한 “interval 언급 없음” 범위 기준에는 어긋납니다.
처음에는 사실 보존으로 통과 판정했으나 독립 검토에서 기준 해석의 변경을 발견했습니다.
**엄격한 사전 기준 6/8, 사실 보존만 보는 보조 판정 7/8을 모두 남겼습니다.**
따라서 짧은 지침도 퇴행 없는 개선으로 채택할 근거는 부족합니다.

위 보완 문구를 넣은 새 지침은 아직 재실험하지 않았습니다. 기존 실험 후보는 그대로 보존했습니다.

Codex는 기본 조건부터 좋은 결과라 추가 지침의 품질 이득을 확인하지 못했습니다.
세 조건의 답변 총 글자 수는 1,098 / 1,104 / 1,104자였습니다.
Opus는 1,685 / 1,566 / 1,452자, Grok은 공통 7개 과제에서 854 / 813 / 822자였습니다.
짧다는 사실 자체를 더 좋은 글이라는 뜻으로 해석하지 않았습니다.

Opus CLI의 8회 비용 추정 합계는 기본 $0.097302, 짧은 지침 $0.113742,
전체 지침 $0.531143이었습니다. 실제 청구 금액은 아닙니다.
전체 지침 조건은 참조 파일까지 모두 넣었으므로, 필요한 내용만 읽는 실제 스킬의 비용과
동일시할 수 없습니다. 모델 간 비용·속도 순위를 매기는 실험도 아닙니다.

## 그대로 도입하면 안 되는 부분

- 숫자 보존 검사가 `최대10회 → 최대20회`를 놓쳤습니다.
- 계약 JSON의 중복 키가 앞의 보호 항목을 지워도 통과했습니다.
- 잘못된 입력 타입에서 약속된 입력 오류 처리 대신 traceback이 나왔습니다.
- 설치 검사가 파일 대신 디렉터리나 문자열이 아닌 설명 필드를 정상으로 보았습니다.
- Git 설정에 따라 실제 스테이징된 서브모듈 변경을 “변경 없음”으로 보고했습니다.

의미를 검사하지 못한다는 한계와 별개로, 문자·설정·변경 범위를 확인하는 기능에서도
수정할 점이 있다는 뜻입니다. 원본은 보존했고 재현 코드와 관측 결과를 남겼습니다.

첨부 자료의 평균 문장당 어절 수 약 79% 감소(27.429 → 5.885)도 읽기 쉬워졌다는 실험 결과가 아닙니다.
문장은 14개에서 61개로 늘었고 전체 글자 수는 1,538자에서 1,537자로 거의 같았습니다.
한국어 문장을 무조건 잘게 끊거나 단어 수를 제한하는 규칙은 권하지 않습니다.

## 어떻게 적용할 것인가

1. 요청 언어·형식, 조건·수치·예외·불확실성을 보존합니다.
2. 제안·구현·검증·배포와 “미제공·미확인·미실행”을 구분합니다.
3. 답부터 말하고 작업에 필요한 구조만 씁니다.
4. 기존 지침과 중복되는 내용은 추가하지 않습니다.

이 저장소는 이미 한국어 보고와 근거 보존 지침이 있어 첨부 블록 전체를 더할 필요가 적습니다.
새 스킬은 복잡한 문서 작성에서 근거 수집·형식 유지가 반복해서 실패할 때 검토하는 편이 낫습니다.
기존 `korean-writing-editor`를 초안 작성·작업 보고까지 확장하거나, 교사 문체의 제품 생성
프롬프트에 개발자 문체를 일괄 적용하는 것은 권하지 않습니다.
