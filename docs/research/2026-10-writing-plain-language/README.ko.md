# 익숙한 말로 쓰는 한국어 기술 문서

[English](README.md)

현재 개인용 스킬은 [Readable(리더블) 0.6.0](../2026-10-readable-rename/README.ko.md)이며
`$readable`로 호출합니다. 아래 이름·경로·결과는 당시 실험 기록입니다.

**개인용 Codex 스킬을 0.5.1로 갱신하고 설치 후 호출까지 확인했습니다.**
최종본은 합성 과제 8개 작성, Opus·Grok 검토 8개, 기존 기능 검사 3개, 설치 후 검사
1개를 통과했습니다. 개인용 읽기·사실 보존 기준의 통과이며, 앞선 비교 실험의 우월성
기준을 통과한 것으로 바꾸지는 않습니다.

이전 글은 서로 구분하기 어렵고 용어도 자연스럽지 않다는 독자 피드백에서 시작했습니다.
이번에는 낯선 이름을 나열하는 대신 누가 무엇을 하는지 설명하도록 바꿉니다. 코드 이름과
명령, 숫자, 조건, 확인되지 않은 사실은 원래 의미를 지켜야 합니다.

## 수정하면서 발견한 문제

- 0.4.0: 글 12개를 받았습니다. 용어 일부는 나아졌지만 백필·롤백 리허설·백분위가
  설명 없이 남았고, 권한 설명은 같은 내용을 반복했습니다. 채택하지 않았습니다.
- 0.4.1: 글 8개를 받았습니다. 기존 데이터를 새 필드에 채우는 작업과 p95를 풀어
  설명했습니다. 하지만 30초 안이라는 문구 아래에 30초 이후의 처리까지 묶는 오류가
  생겼고, 업로드 설명에는 뜻을 풀지 않은 digest가 남았습니다. 채택하지 않았습니다.
- 0.4.2: 글 8개와 비교 평가 12개를 받았습니다. 기존 설치본과 비교해 1승·2패·3건
  판정보류로 채택 기준에 못 미쳤습니다. 현재 화면과 예정된 문구를 혼동한 오류를
  교차 평가에서 발견했습니다. 작성자 대조가 처음에는 놓친 오류입니다. 원래 작업
  이름을 없애 문서·명령과 대조하기 어려워진 부분도 있었습니다.
- 0.4.3: 글 8개와 비교 평가 12개를 받았습니다. 2승·0패·4건 판정보류로, 고정했던
  4승 기준을 통과하지 못했습니다. 이 결과도 그대로 남기며 설치하지 않았습니다.
- 0.5.0: 글 8개를 각각 다른 제공자에게 검토받았습니다. 7개는 통과했지만 업로드
  재요청의 조건을 빠뜨린 단정 두 문장이 발견되어 채택하지 않았습니다.
- 0.5.1: 그 단정을 고치고 실제로 반복된 어색한 표현에 문맥별 예시를 추가했습니다.
  개인용 설치 대상인 Codex에서 여덟 과제를 모두 작성하고 Opus·Grok이 네 개씩 검토합니다.
  여덟 검토 모두 의미 오류와 핵심 이해를 막는 문제가 없다고 판정했습니다.
  스테이징 범위·JSON·서브모듈 검사와 설치 후 호출도 통과했습니다. 설치 파일 여섯 개는
  고정한 후보와 일치하며, 이전 0.2.2는 Git 밖에 백업했습니다.

0.4.0과 0.4.1은 작성자 검토에서 탈락해 예정했던 모델 비교와 설치 검사를 생략했습니다.
0.4.2는 비교를 완료했지만 채택하지 않았습니다.
실패가 확인된 후보를 더 평가하는 비용을 줄인 것이며, 승패 결과가 있는 것처럼
집계하지 않습니다. 실패한 글과 후보도 보존했습니다.

기존 독자 비교에 나온 세 과제와 새로 만든 한국어 원자료 과제 세 개를 씁니다.
추가 두 과제는 0.4.1에서 처음 사용했고, 0.4.2에서는 이미 본 문제를 다시 검사하는
용도입니다. 설치본이 작성한 여섯 글은 재사용하며 새 호출로 세지 않습니다.

0.5.0 실행 전에 채택 판단 방식을 바꿨습니다. 기존의 모델 선호 4승 기준은
통과하지 못한 실험으로 남깁니다. 사용자가 맡긴 개인용 품질 판단에 맞춰, 용어를
이해할 수 있는지와 사실을 지키는지를 직접 검사하는 [별도 기준](personal-design.md)을
정했습니다. 0.5.1은 실제 설치 대상인 Codex에서 작성하고 다른 두 제공자가 검토합니다.
이 범위 변경은 실행 전에 [설계](native-design.md)에 기록했습니다. 과거 비교를 통과로
바꾸거나 다른 모델의 작성 품질까지 보장하는 결정이 아닙니다.

이 검사는 개인용 도구의 채택 근거입니다. 사람이 얼마나 빨리 이해하는지, 어떤 말을
얼마나 자주 쓰는지, 모든 문서에서 기존 방식보다 나은지는 측정하지 않았습니다.

## 실제로 달라진 설명

- 이벤트 처리의 “소비자”를 “이벤트를 받아 처리하는 쪽”으로 씁니다.
- dual-write는 “기존 필드와 새 필드에 함께 저장하는 방식”으로 설명합니다.
- nullable은 “null을 저장할 수 있다”로 풀어 쓰며 빈 문자열과 혼동하지 않습니다.
- 원래 명칭과 코드 식별자는 문서나 명령에서 찾아야 하는 곳에 남깁니다.
- 현재 상태와 계획, 조건이 맞을 때만 가능한 동작을 구분합니다.

이는 문맥에 맞춘 예시이며 단어를 일괄 치환하는 규칙이 아닙니다.
