# pre-sdd-review 스킬은 일반 리뷰보다 효과적인가?

2026년 10월 8–9일 macOS에서 수행한 실측 보고서입니다.
[영문 보고서](README.md) · [사전 실험 계획](method.md) · [실행별 결과](results.json) · [수정안·절차·재사용 검증](followups.json)

2026-10-09 후속 기록: 이 실험과 6.1.3 개발 수정은 이후 커밋됐고, 사용자는 **이 실험을 근거로 판단해 pre-sdd-review·sddx·waygent 세 스킬을 선셋했다**고 기록 갱신 대화에서 직접 설명했습니다. [학습 사례](../../learning/cases/2026-10-08-pre-sdd-review-value.md)에 실험 의도·선택지·교훈을, [선셋 기록](../../learning/cases/2026-10-09-retire-workflow-skills.md)에 실제 삭제와 보충한 이유를 남겼습니다. 아래 권고와 검증 내역은 사용자의 최종 선셋 결정 전, 실험 종료 당시의 판단입니다. 직접 측정한 대상은 해당 합성 사례의 pre-sdd-review이며 세 스킬 전체의 성능을 비교한 실험으로 확대하지 않습니다.

사용자는 이전 모델에는 이런 하네스가 효과적이었지만 최신 모델의 성능 향상으로 필요성이 줄어든 것 같다고 설명했습니다. 이는 선셋의 맥락을 설명하는 사용자 경험과 해석입니다. 이번 실험에서 과거·최신 모델을 동일 조건으로 비교해 변화의 원인까지 검증한 것은 아닙니다.

## 판단부터 말하면

**이번에 시험한 작은 단일 계획에서는 스킬을 쓰는 것보다 일반 리뷰가 효율적이었습니다.** 일반 리뷰도 실제 결함을 모두 찾았고, 스킬은 추가 결함을 발견하지 못했습니다. 대신 시간이 늘었고, Claude에서는 불필요한 수정 요구도 나왔습니다.

그렇다고 효과가 전혀 없는 것은 아닙니다. 스킬을 사용하면 **수정한 문서를 다른 검토자가 다시 확인하고, 무엇을 검토·수정했는지 문서 해시와 함께 기록하는 절차**가 생깁니다. 이 절차는 실제로 작동했습니다. 다만 이번 실험에서는 그 절차 덕분에 결함을 하나 더 막았다는 결과까지 나오지는 않았습니다.

따라서 현재 권고는 다음과 같습니다.

- **작고 명확한 단일 계획:** 일반 리뷰를 사용합니다.
- **수정 후 별도 검토와 추적 가능한 인계 기록이 필요한 작업:** 그 추가 비용을 감수하고 스킬을 사용합니다.
- **대규모 계획, 여러 계획이 얽힌 작업, 보안·마이그레이션·동시성 문제:** 이번 실험으로 효용을 판단할 수 없습니다.

반복 재현된 오탐을 줄이는 한 문단 수정은 **로컬 개발 버전 6.1.3**에 반영했습니다. 이는 기존 스킬의 문제를 줄인 개선이지, 수정된 스킬이 일반 리뷰보다 우수하다는 증거는 아닙니다. 스킬 삭제, 대대적인 축약, 공식 지원 호스트 확대는 하지 않았습니다.

## 무엇을 어떻게 비교했나

주 비교에서는 **6.1.2 전체 파일을 고정**했습니다. 작업 중 수정안을 적용한 이후에도 주 비교에는 같은 6.1.2를 사용했습니다.

- 핵심 비교: **62개 실행, 정상 완료 60개, 시간 제한 종료 2개**.
- 수정안 검증: 8개 실행.
- 이전 검토 재사용 검증: 2개 실행.
- 합계: **평가 실행 72개**. 모델 식별용 호출과 잘못 구성된 초기 실험은 제외했습니다. 하위 검토자 호출은 이 실행 수와 별개이며, 확인 가능한 사용량에는 포함했습니다.

고정한 `SKILL.md`의 SHA-256은 다음과 같습니다.

```text
d621401f528cdd2da43c6f78e73805d168813ed03542a33a51bcc4984773933f
```

원본은 커밋 `f4e659b23f2f808ed6cce0e86de4bc1043526e99`에서 복원할 수 있습니다.

| 조건 | 모델에게 제공한 것 | 비교 목적 |
| --- | --- | --- |
| 일반 리뷰(`plain`) | 구현 전 준비 상태 검토라는 동일한 목표, 승인된 결정과 수정 범위에 대한 동일한 제한. 스킬·하위 검토자 없음 | 모델이 직접 수행하는 일반 리뷰 |
| 전체 스킬(`skill`) | 고정한 스킬, 별도 검토자, 증거 기록 절차. 탐지 실험에서는 review-only 모드 | 추가 모델 작업을 포함한 전체 절차의 효과 |
| 검토 지침만(`protocol`) | 수정하지 않은 reviewer protocol만 제공. 모델 한 개가 직접 검토하고 별도 조정·기록·위임 절차는 생략 | 지침 내용과 전체 절차의 차이를 보는 보조 비교 |

실제 개인 프로젝트 대신 [합성 저장소 4개](harness/fixtures/)를 만들었습니다. 정답 기준은 검토 대상 저장소나 모델 프롬프트에 넣지 않았습니다.

| 사례 | 내용 | 실제 결함 | 기대 판정 |
| --- | --- | ---: | --- |
| a | 필요한 동작과 테스트가 명확한 정상 계획 | 0개 | READY |
| b | 승인된 빈 문자열 동작 누락, 존재하지 않는 검증 명령 | 2개 | REVISE |
| c | 빈 문자열 처리 방식을 제품 책임자가 아직 결정하지 않음 | 1개 | BLOCKED |
| d | 생산자 변경과 실제 소비자 계약의 충돌, 실행되지 않는 하위 폴더 테스트 | 2개 | REVISE |

**고유한 결함은 5개입니다.** 여러 번 실행했다고 서로 다른 결함 수십 개를 검증한 것은 아닙니다. a와 d는 한 번 더 반복했고, 지침만 사용하는 조건도 a와 d에 적용했습니다. 문서 자동 수정과 수정 후 재검토는 b에서 따로 시험했습니다. 모든 저장소의 기존 테스트는 계획한 기능을 구현하기 전 상태에서도 통과합니다.

[오라클 검사](harness/test_oracle.py)에서는 결함의 근거를 실제 코드로 확인했습니다. 생산자만 바꾸면 소비자가 실패하는지, 하위 폴더 테스트가 실행에서 빠지는지, 계획된 정확한 비교가 공백 제거·대소문자 변경 같은 잘못된 구현을 잡는지 검사했습니다. 접두사만 검사하는 약한 테스트가 같은 잘못된 구현을 통과시키는지도 확인했습니다. 이 검사는 정답 기준을 뒷받침하며, 모델의 일반적인 품질을 증명하지는 않습니다.

## 결함 탐지 결과

모델별로 일반 리뷰와 전체 스킬을 각각 6번 실행했습니다. a/b/c/d를 한 번씩, a/d를 한 번 더 검토했습니다.

표의 ‘발견’은 **완료되고 채점된 실행에서의 결함 발견 기회**를 합산한 값입니다. ‘오탐’은 선택적 조언이 아니라, 근거 없이 반드시 고쳐야 한다고 요구한 항목입니다.

| 모델 | 일반 리뷰: 완료 / 발견 / 오탐 | 전체 스킬: 완료 / 발견 / 오탐 | 중앙시간: 일반 → 스킬 |
| --- | --- | --- | --- |
| Sol 6.1/high | 6/6; 7/7; 0 | 6/6; 7/7; 0 | 39.9초 → 120.7초 |
| Astra/high | 6/6; 7/7; 0 | 6/6; 7/7; 0 | 36.7초 → 142.1초 |
| Opus 5.5/high | 6/6; 7/7; 0 | 6/6; 7/7; 2 | 28.5초 → 94.9초 |
| Grok 4.7 Build/high | 6/6; 7/7; 0 | 5/6; 6/6; 0 | 255.1초 → 597.5초 |

이 탐지 비교는 48개 실행 중 47개가 완료됐습니다. **완료된 리뷰에서는 양쪽 모두 실제 결함을 전부 찾았습니다. 추가로 확인된 실제 결함도 없었습니다.**

- 일반 리뷰의 최종 판정: 24/24 정확.
- 전체 스킬의 최종 판정: 완료된 23개 중 22개 정확. 별도로 시간 초과 1개.
- 문제 있는 계획을 잘못 READY로 승인한 사례: 양쪽 모두 관찰되지 않음.

Grok의 스킬 조건에서는 c가 시간 초과였으므로, 위 중앙시간은 서로 다른 사례 구성을 비교합니다. **양쪽 모두 완료된 같은 5쌍만 비교하면 일반 269.6초, 스킬 597.5초**입니다. 901.4초에 중단된 실행은 별도의 완료 실패로 남겼습니다.

시간에는 주 에이전트의 작업과 하위 검토자를 기다리는 시간이 포함됩니다. 시간 초과는 최종 판정을 받지 못한 실패이며, 임의로 ‘결함을 못 찾았다’거나 ‘판정이 틀렸다’고 채점하지 않았습니다. 동일한 원인에서 나온 동작 누락과 테스트 누락을 따로 지적해도 실제 결함 수는 한 번만 셉니다.

채점은 모델·조건 표시를 가린 보고서를 별도 LLM 채점 에이전트가 정답 기준과 대조하는 방식으로 했습니다. 논쟁적인 주장은 주 에이전트가 실행 가능한 반례와 대조했습니다. 사람 전문가 패널의 평가도, 완전히 독립적인 타 공급자 모델의 평가도 아닙니다. Sol의 수정안 확인 2개는 주 에이전트가 조건을 알고 채점했으며 결과 파일에 따로 표시했습니다.

### 스킬에서 나온 불필요한 요구

Claude의 원래 스킬 조건에서 중요한 오탐이 2건 나왔습니다.

1. **c 사례:** 이미 입력 범주별 정확한 테스트와 결과를 결정하는 불변 조건이 있었는데, 구체적인 입력 문자열과 출력 예시를 더 나열해야 한다고 요구했습니다.
2. **a 반복 사례:** 정확한 입력·출력 5개와 실제 테스트 실행 확인까지 적혀 있는데, 테스트 메서드 이름까지 지정해야 한다고 요구했습니다. 정상 계획을 잘못 `REVISE`로 판정했습니다.

일반 리뷰의 설명도 모두 완벽하지는 않았습니다. 일부는 기존 소비자 계약 충돌 때문에 테스트가 실패할 상황인데도, 원래 계획대로 하면 테스트가 성공 종료한다고 과장했습니다. 테스트 탐색 누락이라는 실제 결함 자체는 유효했으므로, 이를 추가 오탐보다는 근거 설명의 부정확성으로 구분했습니다.

Grok의 c/스킬 실행은 900초 제한에 걸렸고 기록도 미완료로 남았습니다. 하위 검토자의 의견은 있었지만 주 에이전트가 이를 판정해 최종 답변을 만들지 못했습니다. 중간에 나온 `REVISE`를 최종 판정으로 채점하지 않았습니다. 같은 사례의 일반 리뷰는 86.147초에 완료됐습니다.

비용 집계에는 다음 제한이 있습니다.

- Claude·Grok 금액은 CLI가 보고한 추정치이며 실제 청구서가 아닙니다. Codex는 비교 가능한 달러 비용을 보고하지 않아 임의 가격을 대입하지 않았습니다.
- Claude는 같은 메시지가 여러 번 기록되는 것을 메시지 ID로 중복 제거하고 하위 검토자 기록을 포함했습니다. Codex는 서로 다른 세션의 사용량을 합산했습니다.
- Grok의 상위 사용량에는 하위 모델 호출이 포함됩니다. 하위 사용량을 다시 더하지 않았습니다.
- Grok의 유효한 실행에서 확인된 비용은 **최소 $2.6761**입니다. 시간 초과 두 건의 전체 비용은 알 수 없습니다. 비교에서 제외한 초기 도구 설정 오류 실험도 **최소 $0.8777**을 사용했으며, 이 역시 완전한 합계가 아닙니다.
- Claude는 핵심 16개 실행에서 **$5.1621**, 수정안 후속 6개에서 **$3.1893**을 보고했습니다. 모델 식별용 호출은 제외한 수치입니다.

따라서 **이 연구 전체의 정확한 달러 비용은 계산할 수 없습니다.** 미보고 비용을 0으로 취급하지 않았습니다. 공급자마다 토큰·캐시 계산 방식도 다르므로, 원시 토큰 수를 곧바로 공급자 간 비용 비교로 해석하면 안 됩니다.

전체 스킬은 지침 분량, 위임, 기록 절차와 모델 작업량을 함께 늘립니다. 동일 토큰 예산을 강제한 비교는 아닙니다. 이 실험만으로 어느 구성 요소가 비용 증가의 전부를 만들었다고 분리해 말할 수는 없습니다. 지침만 사용하는 새 제품 모드도 추가하지 않았습니다.

여기서 확인한 스킬의 추가 가치는 **별도 검토자의 수정 확인과 문서 해시를 포함한 추적 기록**입니다. 이번 작은 사례에서는 수정 후 검토자가 추가 결함을 찾아내지는 않았습니다. 수정된 계획을 실제 제품에 구현하거나 이후 운영 결함률을 측정한 실험도 아닙니다.

### ‘별도 에이전트’가 곧 ‘독립 검증’은 아니었다

실제 지시문과 실행 기록도 별도로 조사했습니다.

- 본 실험의 전체 스킬 27개 실행·검토자 호출 32회와 후속 8개 실행·호출 8회를 확인했습니다. 새 문맥의 하위 검토자는 39개, 누락 필드 보완을 위한 재개는 1개였습니다.
- Codex의 조사 대상 호출 16개는 모두 `fork_turns: none`과 별도 자식 세션을 사용했습니다. 저장된 지시문 본문이 암호화돼 있어 결함 단서 전달 여부는 확인할 수 없었습니다. 복호화를 시도하지 않았습니다.
- Claude의 읽을 수 있는 discovery 지시문 3개에는 unittest 하위 폴더 탐색이나 `__init__.py`에 대한 구체적인 단서가 들어 있었습니다. 주 비교 d의 두 실행과 수정안 d 실행입니다. 전체 절차가 결함을 찾았다는 점은 인정하지만, 무힌트 독립 재발견의 증거로 보지 않았습니다.
- 세 모델의 전체 스킬 수정 실행에서는 발견 단계와 수정 후 확인 단계에 서로 다른 검토자가 참여했습니다. 파일 해시를 대조해 계획 문서만 바뀌었고 두 원인 결함이 고쳐졌음을 확인했습니다. 기록의 `reviewers: 1`은 논리적인 역할 수이며 누적 에이전트 수가 아닙니다.
- Grok의 d 반복 실행은 외부 고객이 없는 내부 데이터 변경을 `data-boundary` 위험으로 넓게 해석해 추가 검토자를 호출했습니다. 의미상 오탐과는 별개로, 불필요하게 절차와 비용이 늘어난 사례입니다.

기록이 있으면 주장을 확인하기 쉬워집니다. **기록 자체가 판단의 정확성이나 독립성을 보장하지는 않습니다.**

## 실제로 적용한 개선

이 연구가 측정한 스킬의 `reviewer-protocol.md`에 한 문단을 추가했습니다. 그 스킬은 지금 트리에 없습니다. 취지는 다음과 같습니다.

> 계획에 적힌 검증과 불변 조건을 그대로 고려한다. 어떤 잘못된 구현이 이미 정해진 검증에서 실패한다면, 그 구현을 검증 공백의 반례로 쓰지 않는다. 입력 범주가 명시돼 있고 승인된 동작으로 기대값이 결정된다면 구체적인 테스트 데이터를 고르는 일은 구현 세부사항이다.

수정 전후의 검토 지침 SHA-256은 다음과 같습니다.

```text
기존: 195b3cc04363769c6deb75b5b73544c039bf3b9f6b804a70e0f22b1e2eab7c9d
후보: 5d70337be164a9e27d60512520118f419273b2ac0faaaa8786ef76dee8ebce40
```

후보 실험에서 `SKILL.md` 자체는 바꾸지 않았습니다. 참조 지침만 바뀌었으므로 `SKILL.md` 해시만 확인했다면 두 조건의 차이를 놓쳤을 것입니다. 전체 파일 목록과 지침 해시를 별도로 기록했고, 파생 해시는 [후속 결과](followups.json)에 보존했습니다. 저장소의 측정 규칙도 변경된 참조 파일 또는 전체 리소스 목록의 해시를 확인하도록 보완했습니다.

| 후속 검증 | 기존 지침 | 수정 지침 |
| --- | --- | --- |
| c, 새 세션으로 두 쌍 비교 | 구체적인 문자열 예시를 더 요구하는 동일 오탐 2/2 | 실제 제품 결정 누락만 유지, 해당 오탐 0/2 |
| 정상 계획 a, Claude | 주 비교 반복에서 잘못 REVISE | READY, 중요한 지적 없음 |
| 여러 파일이 얽힌 d, Claude | 실제 결함 2개 발견 | 두 결함 유지. 다만 지시문에 단서가 있어 독립성 주장에는 제한 |
| a와 d, Sol/high | 주 비교를 기준으로 대조 | 정상 READY와 실제 결함 2개 탐지 유지 |

조건 표시를 가린 별도 채점도 c의 차이를 확인했습니다. 다만 형식·절대 경로·일부 호스트 이름으로 조건이 드러날 수 있어 완전한 맹검은 아닙니다. 추가 문단의 핵심 의미가 실제 검토자 지시문에 전달된 것도 확인했지만, 항상 원문 그대로 전달된 것은 아니었습니다.

별도 최종 리뷰에서는 중요한 의미상 회귀가 발견되지 않았고, 오래된 버전 응답 예시 하나를 바로잡았습니다. 로컬 6.1.3에는 이 문단, 버전·버전 응답 값, Unreleased 기록, 유지보수 계약을 함께 반영했습니다. 실제 검증 누락, 소비자 계약, 테스트 탐색, 상태 분할, 동시성 검사 기준은 유지했습니다. 지원 호스트, 기록 스키마, 기본 모드, 수정 범위는 바꾸지 않았습니다.

**이는 반복 재현된 특정 오탐을 줄인 결과입니다. 두 쌍의 비교만으로 통계적 우월성이나 모든 저장소에서의 품질 향상을 주장할 수 없습니다. 일반 리뷰보다 낫다는 결론도 아닙니다.**

## 이전 검토 결과의 재사용도 별도로 점검했다

기존 재사용 규칙의 변경 목록은 현재 저장소를 이전 `HEAD`와 비교합니다. 이전 검토 당시의 커밋되지 않은 작업 상태 자체와 비교하지는 않습니다.

[오프라인 반례](harness/reuse_counterexample.py)에서는 다음 틈을 재현했습니다. 검토 당시 변경돼 있던 소스를 원복하면, 소스 내용은 달라졌는데도 HEAD와 문서 해시는 같고 규칙이 확인하는 변경 목록은 비어 있을 수 있습니다. 검토 당시 있던 미추적 파일을 삭제해도 같은 문제가 생깁니다.

실제 Sol/high에서도 두 세션으로 시험했습니다. 미추적 검증 실행 파일이 존재하는 상태에서 READY를 받은 뒤 그 파일만 삭제하고, 같은 저장소·기록으로 새 세션에 동일한 요청을 보냈습니다. **잘못된 READY는 나오지 않았습니다.** Sol이 저장소를 다시 확인해 검증 명령 누락을 발견하고 REVISE를 반환했습니다.

따라서 정적으로는 재사용 조건이 불완전하지만, 실제 모델의 잘못된 승인은 재현하지 못했습니다. 실패가 나올 때까지 추가로 반복하지 않았습니다.

향후에는 이전 검토 시 문서 외 변경·미추적 입력이 있었는지 기록하거나 그 내용의 해시를 보존하는 방법을 검토할 수 있습니다. 모든 미커밋 상태의 재사용을 금지하면 정상적인 문서 수정 후 재사용도 막히므로 별도의 설계와 검증이 필요합니다. 이번 한 문단 수정에는 이 기록 스키마 변경을 포함하지 않았습니다.

## 재현과 실제 검증 범위

[실험 실행기](harness/run.py)는 명시적으로 실행할 때만 실제 모델을 호출합니다. 기본 검증이나 CI에는 포함하지 않았습니다. 기준 커밋의 스킬 전체 파일을 고정한 뒤 모든 단계에 `--skill-root`를 전달합니다.

```sh
python3 docs/research/2026-10-pre-sdd-review-eval/harness/run.py \
  --engine sol --stage discovery --parallel 2 \
  --skill-root /absolute/path/to/frozen/pre-sdd-review \
  --output /absolute/path/to/new-external-cells
```

다른 단계는 `repeat`, `protocol`, `repair`입니다. 기존 실행 디렉터리를 덮어쓰지 않습니다. `harness/oracle.json`은 채점용이며 모델 입력이 아닙니다. 초기 CLI 인자·도구 설정 오류와 재시도 내역은 [실험 계획의 실행 변경 기록](method.md#execution-amendments-and-attrition)에 따로 남겼습니다.

원본 공급자 기록, 전체 응답, 생성된 실험 저장소는 Git에 넣지 않았습니다. 모든 호출이 끝난 뒤 작업용 인증 복사본 57개를 제거했고 사용자 원본 인증은 바꾸지 않았습니다. 저장소에는 합성 입력, 코드, 요약한 채점 결과와 파생 수치만 보관합니다.

실제로 수행한 검증은 다음과 같습니다.

- `python3 scripts/verify.py --skill pre-sdd-review`: 버전 복사본과 Unreleased 개발 버전 처리 규칙을 맞춘 뒤 통과했습니다.
- `python3 scripts/verify.py`: **현재 변경을 staging한 별도 로컬 체크아웃에서 1,286개 테스트와 컴파일을 통과했습니다.** 패키징은 Git 인덱스의 파일을 읽으므로 원래 저장소의 미스테이징 상태에서는 이전 6.1.2를 읽어 버전 불일치가 났습니다. 전역 임시 `GIT_INDEX_FILE` 방식도 하위 테스트 저장소가 같은 인덱스를 상속해 적합하지 않았습니다. 별도 체크아웃으로 검증해 원래 작업 트리와 staging 상태를 보존했습니다.
- `harness/test_oracle.py`: 공급자 호출 없이 6개 검사를 Python 3.14와 macOS 기본 Python 3.9에서 통과했습니다. 합성 입력과 반례의 타당성을 검사한 것이며 모델 품질 검사는 아닙니다.
- 문서 검사 68개를 통과했습니다. 연구용 Python 파일 21개가 최종 집계 수정까지 포함해 Python 3.9에서 컴파일됐습니다. 로컬 Markdown 링크와 `git diff --check`도 통과했습니다. 제품·테스트·릴리스 스크립트의 변경된 내용은 전체 검증에 사용한 내용과 일치했습니다.
- 커밋, 태그, 패키지 배포, 공식 지원 호스트 확대, push는 하지 않았습니다.

위 검증은 실험 및 스킬 수정 시점의 기록입니다. 이 한국어판은 기존 결과를 번역·정리한 문서이며 추가 모델 실험을 수행하지 않았습니다.

## 그래서 언제 쓰면 좋은가

| 상황 | 현재 근거에 따른 선택 |
| --- | --- |
| 작고 명확한 단일 계획에서 실제 문제와 수정 방향만 필요 | 일반 리뷰 |
| 수정·기록 절차 없이 구조화된 검토만 필요 | 지침만 쓰는 조건도 결과는 유지했지만 일반 리뷰보다 낫지는 않았음 |
| 수정 후 별도 확인과 문서 버전에 연결된 인계 기록이 필수 | 공식 지원 Codex에서 전체 스킬 사용. 실제 검토 내용도 확인 |
| 큰 계획 묶음, 동시성, 마이그레이션, 인증·보안, 공개·비공개 데이터 경계 | 이번 실험으로 판단할 수 없음 |
| Claude·Grok에서 정식 운영 | 이번 탐색 실험만으로 공식 지원이 입증되지는 않음 |

작은 합성 사례에서는 일반 리뷰부터 정답을 모두 찾았기 때문에 개선 효과를 보이기 어려웠습니다. 같은 5개 결함을 더 많이 반복해도 넓은 범위의 동등성을 증명할 수 없습니다. 캐시, 도구와 샌드박스 차이, 공급자 부하, 모델별 병렬 실행 수준도 시간에 영향을 줍니다.

특히 Claude의 별도 검토자는 명령 실행 도구가 없고 주 에이전트와 일반 리뷰는 안전한 기존 테스트를 실행할 수 있었습니다. 이것도 이번에 비교한 전체 작업 방식의 차이에 포함됩니다. 고정한 스킬을 명시적으로 호출했으므로 자동 활성화 품질, 실제 설치 과정, 운영 신뢰성, 장기적인 투자 대비 효과까지 검증한 것은 아닙니다.

다음 개선이 필요하다면 같은 작은 사례를 반복하기보다 다음 질문을 검증해야 합니다.

1. 길거나 서로 영향을 주는 실제적인 계획에서 일반 리뷰가 놓친 중요한 결함을 스킬이 추가로 찾는가? 잘못된 READY, 수정 후 확인 성공률, 사람이 다시 고치는 수고까지 측정해야 합니다.
2. 별도 검토의 독립성이 중요하다면 주 에이전트가 보낸 지시문과 추가 검토자 호출 조건도 확인해야 합니다. 새 에이전트를 만들었다는 사실만으로 충분하지 않습니다.
3. 이전의 미커밋·미추적 소스 상태를 놓치는 재사용 조건은 별도로 보완하되, 정상적인 문서 수정 후 재사용까지 막지 않는지 검증해야 합니다.

**현재 선택은 ‘스킬을 항상 켜기’보다 ‘일반 리뷰를 기본으로 하고, 별도 검토·기록 절차가 필요한 경우에만 스킬을 쓰기’입니다.**
