# 책 쓰기 스킬을 만든다면 어떻게 설계할까?

결정일·기록일: 2026-11-20.
관련 작업: 책 쓰기 스킬 설계, 같은 날 `kws-book-writer` 0.1.0 구현과 실행 검증.
결과: 저장소 제품 `kws-book-writer`로 구현했습니다. 스모크 1회, 결함 심기 평가 30회, 파일럿 1권을 실제로 실행했습니다. 사용자의 파일럿 채택 판단은 아직 받지 않았습니다.
근거 성격: 설계는 공개된 책 쓰기 작업 흐름들을 읽고 관찰한 패턴과 이 저장소의 과거 측정 기록에 기댑니다. 구현 뒤 결과는 [평가 기록](../../research/2026-11-kws-book-writer-eval/README.md)의 실제 실행입니다.
초안을 쓴 뒤 대화 기록을 물려받지 않은 새 에이전트가 비판 검토를 한 번 했고, 그 지적을 원본 기록과 대조해 반영했습니다.

## 시작한 문제

사용자는 여러 장으로 된 한국어 기술서 초고를 쓰는 스킬을 이 저장소에 만들고, 실제로 돌려 검증한 뒤
그 결과로 개선하자고 했습니다. 설계는 작성자가 만족할 때까지 다듬기로 했습니다.

만족 기준은 초안을 쓰기 전에 정했습니다.

- 모든 구성 요소에 근거 표시가 있다.
- 직접 호출 전용, 레거시 금지, Python 3.9, 새 스킬 기본 불허 규칙과 충돌하지 않는다.
- 새 에이전트의 비판 검토를 한 번 받고, 그 지적을 확인해 한 번 고친다.

## 당시 조건

- [CONTRIBUTING](../../../CONTRIBUTING.md)은 새 스킬을 기본적으로 받지 않습니다.
  저장소 제품으로 만들려면 먼저 운영 규칙을 바꿔야 합니다.
- 정식 스킬은 [직접 호출할 때만](2026-10-24-explicit-skill-invocation.md) 씁니다.
  레거시 경로와 별칭은 남기지 않습니다. 제품 스크립트는 macOS 기본 Python 3.9에서도 돌아야 합니다.
- [인사이트](../insights.md): 절차를 추가하려면 구체적인 효용이 있어야 합니다.
- 이미지·동영상 제품은 [2026-10-28에 종료](2026-10-28-retire-image-workbench-and-simplify-repository.md)했습니다.
- [Readable 사례](2026-10-09-personal-technical-writing.md): 모델 평가로는 자연스러움을 검증하지 못했고,
  사용자는 익명 비교 세 쌍을 모두 구분하기 어려웠다고 설명했습니다.
- [AI 티 스킬 검토](2026-10-09-slop-skills-quality.md): 문자열 기반 한국어 게이트는 의미가 뒤집힌 문장을 통과시켰습니다.

## 참고한 근거

| 표시 | 뜻 |
| --- | --- |
| [외부관찰] | 공개된 책 쓰기 작업 흐름의 문서와 산출물을 읽고 확인한 패턴. 이 저장소에서 재현하지 않음 |
| [저장소측정] | 이 저장소에서 측정한 결과 |
| [미측정] | 근거 없는 설계 아이디어 |

외부에서 관찰한 패턴 [외부관찰]:

- 장을 쓴 뒤 책 전체를 새 에이전트가 ACCEPT/BLOCK으로 판정하는 단계가 첫 판정에서 자주 막았습니다.
  사유는 틀린 장 참조, 독자용 본문에 남은 작업 역할명, 약속한 범위 누락, 장부와 어긋난 사실, 목차에 안 잡히는 제목 구조였습니다.
- 장별 사실 검수 로그가 "미해소 없음"이어도 나중 판정이 사실 오류를 찾은 경우가 있었습니다. 검수 로그는 자기 보고입니다.
- 원고 속 `<선택적 사전조건>` 같은 자리표시자가 EPUB 변환에서 HTML 태그로 읽혀 빌드가 실패한 경우가 있었습니다.
- 금지 마커 목록이 파일마다 따로 적혀 어긋나거나, 메타데이터를 따옴표 처리 없이 YAML에 넣는 결함이 있었습니다.
- 사용자가 직접 고치지 않고 무엇을 바꿀지 말하게 해서 문체를 익히는 방식, 진입 파일은 경로 안내와 불변 조건만 두고
  단계 문서는 필요할 때 읽는 구조, 본문 해시가 바뀌면 이전 검토를 무효로 하는 장치, 독자 정의를 한 파일에서만 관리하는 방식.

## 제안한 설계

| # | 구성 | 근거 |
| --- | --- | --- |
| C1 | 직접 호출하는 스킬 하나. `SKILL.md`에는 경로 안내, 불변 조건, 단계별 필수 산출물, 완료 조건. 상세 절차는 `references/` | [외부관찰] 진입 구조. [저장소측정] how-it-works는 참조를 건너뛰다 출력 부분을 빠뜨린 적이 있어 산출물 목록은 진입 파일에 둠 |
| C2 | 작업 폴더(`brief.md`, `research/ledger.md`, `plan.md`, `voice.md`, `chapters/`, `checks/`, `book.json`)와 폴더 상태로 이어 하기 | [외부관찰] 파일로 단계를 넘기는 방식. 이어 하기는 [미측정] |
| C3 | 리서치 장부: 항목마다 ID와 출처 | [외부관찰] 판정이 장부와 대조 |
| C4 | 계획: 용어 표, 장별 오프닝·클로징 배정, 독자 약속, 그림 | [외부관찰] |
| C5 | 확인 지점 두 곳: 계획 승인(필수), 첫 장 보정(기본 켜짐, "끝까지"면 건너뜀) | [저장소측정] Readable. 보정 효과는 [미측정] |
| C6 | 문체 기본값. 숫자 상한은 시작값일 뿐 차단 기준이 아님 | [저장소측정] Readable 용어 처리. 숫자 효과는 [미측정] |
| C7 | 장마다 새 하위 에이전트가 순서대로 저술, 묶음별 사실 검수는 고친 문장 전후를 `checks/factcheck.md`에 남김 | [외부관찰] 자기 보고 검수 로그의 한계 |
| C8 | mermaid 그림과 캡션 | [외부관찰] |
| C9 | 스크립트 조립, 장 경계는 인접한 두 장씩 다듬음 | [미측정] |
| C10 | `scripts/book_check.py`: 확실한 검사만 차단(남은 마커, 수락 뒤 원고 해시 불일치, 메타데이터 오류), 나머지는 보고 | [외부관찰] 마커 목록 불일치, YAML 결함, 자리표시자 빌드 실패. [저장소측정] 문자열 게이트의 한계 |
| C11 | 새 하위 에이전트의 수락 게이트, 한 번 고치고 바뀐 문장만 재판정, 그다음 사용자 결정 기록 | [외부관찰] 첫 판정 차단이 흔했음. 일반 리뷰보다 나은지는 [미측정] |
| C12 | 선택 단계 EPUB 빌드 | [외부관찰] |

측정 뒤 넣을 후보: 병렬 저술, 독자 테스트, 원고 전체 편집 에이전트, effort를 고정한 agent 정의, 장르 확장과 Codex.
넣지 않는 것: 표지 이미지 생성(이미지 제품 종료), 효과 측정이 없는 학습 루프·요청 전용 역할, `korean-writing-editor` 자동 연결, 하위호환 파일.

평가 계획: 책 한 권끼리 A/B 비교는 표본이 1이라 하지 않습니다. 오프라인 회귀 검사, 결함 심기 평가(게이트 유지 여부),
파일럿 한 권(절대 기준)으로 나누고, 판정 규칙은 실행 전에 고정했습니다.

비판 검토가 지적해서 고친 것: 사실 검수 로그를 증거로 쓴 점, 빌드 중 원고 수정 경로에서 해시 잠금이 멈출 수 있던 점,
그림·조립·이어 하기 누락, 평가 계획에 숫자와 대조군이 없던 점, 두 확인 지점의 모순, 근거 없는 문체 상한 숫자.

## 구현과 측정 (2026-11-20)

사용자가 정한 것: 이름은 `kws-book-writer`, 위치는 저장소 제품(새 스킬 금지 규칙을 소유자 결정으로 바꿈),
실행 검증은 스모크·결함 심기·파일럿 전부, 파일럿 주제는 작업자가 사용자의 비공개 백엔드 저장소의 작업 플랫폼으로 정함.
호스트(Claude Code)와 책 종류(한국어 기술서)는 기본값대로입니다.

구현에서 설계와 달라진 점:

- C8 그림 렌더와 C12 EPUB 빌드는 넣지 않았습니다. 이 Mac에 mmdc, pandoc, epubcheck가 없어 돌려 보지 못한 기능을 내보내게 되기 때문입니다. 출력은 마크다운입니다.
- C10에 "장 파일과 조립본이 다르면 실패"를 더했습니다. 해시 잠금은 통과 판정 뒤에만 막고, BLOCK 뒤 수정은 보고만 합니다.
- 마커 목록은 스크립트 한 곳에만 두고, 다른 파일에 마커 문자열이 없다는 것을 계약 테스트로 확인합니다.

실행 결과([평가 기록](../../research/2026-11-kws-book-writer-eval/README.md), 판정 규칙은 실행 전에 [고정](../../research/2026-11-kws-book-writer-eval/preregistration.md)):

- 스모크(합성 3장, $5.03): 두 확인 지점에서 멈췄고 장마다 새 하위 에이전트가 썼으며 `check --final`이 통과했습니다. 헤드리스에서 하위 에이전트가 죽는 문제는 생기지 않았습니다. 조립 스크립트가 목차 제목의 코드 표기를 지우는 결함이 나와 고쳤습니다.
- 결함 심기: 8개 기준을 둔 게이트 24/24, 일반 리뷰 22/24로 기준(4건 차이)에 못 미쳐 "측정된 차이 없음"입니다. 규칙대로 게이트를 일반 리뷰 지시와 작업 폴더 입력으로 바꿨고, 확인 실행에서 24/24였습니다. 깨끗하다고 둔 원고에도 실제 결함이 3가지 있어서 오탐률은 측정하지 못했습니다. 채점자는 조건 이름을 몰랐지만 출력 형식으로 조건을 짐작할 수 있었습니다. 비용은 줄지 않았습니다($7.57 → $7.41, 10회).
- 통과 판정을 받은 스모크 원고에 실제 오류 2건과 렌더링되지 않는 굵은 글씨 8곳이 남아 있었습니다. ACCEPT는 결함이 없다는 증거가 아닙니다. 굵은 글씨는 보고 항목과 문체 규칙으로 막았습니다.
- 파일럿(비공개 저장소, 6장 51,742자): 사실 검수가 실제 수정 19건을 남겼습니다. 조사 단계가 원장 544항목, $24로 비용의 절반을 넘었습니다. 계정 사용 한도에 걸려 게이트 직전에 멈췄고, 새 세션이 작업 폴더 상태만 보고 7단계부터 이어 가 1라운드 ACCEPT로 끝났습니다(전체 약 $47.70). 용어 검사가 '릴리스' 안의 '리스'를 잡는 오탐이 나와 고쳤습니다. 같은 원고를 현재 버전(일반 리뷰 게이트)으로 다시 판정하니 이전 게이트가 통과시킨 실제 오류 4건(응답 코드 2, 장 사이 상태 모순, 재전송 간격)을 찾았고, 고친 뒤 통과했습니다($11.57). 표본 1이라 두 게이트의 우열은 말할 수 없습니다. 전체 실행 비용은 약 $72입니다.

## 유지와 종료 판단

0.1.0을 저장소 제품으로 유지합니다. 사용자 채택은 파일럿 원고를 사용자가 직접 읽고 판단할 때까지 미측정입니다
(무작위 3개 장에서 장당 고칠 곳 5곳 이하, "쓸 만하다"는 판단).
다음에 측정할 후보: 조사 비용 상한, 문단당 식별자 밀도, 장 사이 모순을 보는 검토.

## 다음에 쓸 배움

- 검수 로그가 "문제 없음"이라고 해도 그 자체는 증거가 아닙니다. 나중 단계가 실제로 무엇을 찾았는지를 봐야 합니다.
- 규칙 기반의 확실한 검사만 빌드를 막고, 휴리스틱 검사는 보고에 그칩니다.
- 해시 잠금 같은 강한 게이트를 두면 정당한 수정 경로도 함께 설계해야 합니다.
- 긴 판정 기준 목록은 심은 결함에서 일반 리뷰보다 낫다는 것을 보이지 못했습니다. 판정 지시보다 원장·검사 보고서 같은 입력이 일을 합니다(천장 근처라 작은 차이는 못 봄).
- 통과 판정 뒤에도 장 사이 모순과 렌더링 결함이 남았습니다. 기계로 확실히 잡히는 것은 스크립트로 옮깁니다.
