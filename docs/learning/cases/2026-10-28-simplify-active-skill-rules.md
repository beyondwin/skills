# 남은 두 스킬에서 어떤 규칙을 줄이고 무엇을 남길까?

결정일·기록일: 2026-10-28.
관련 작업: korean-writing-editor 3.0.1, how-it-works 4.0.1.
결과: 중복·모순 정리, 오프라인 회귀 검사와 전체 저장소 검증 완료. 새 모델 품질 미측정.
근거 성격: 사용자의 다각도 분석·중복 및 불필요한 규칙 정리 요청, 현재 계약과 과거
측정 기록, 정적 검토와 오프라인 회귀 검사. 새 모델 실행은 승인 범위에 없었고
수행하지 않았습니다.

## 시작한 문제

이미지·동영상 제품을 종료한 뒤 남은 두 스킬의 본문과 참조 문서를 검토했습니다.
사용성과 질문 부담, 의미 보존, 규칙의 기준 위치, 시험이 실제로 확인하는 범위,
버전·공개 안내의 일관성을 나누어 조사했습니다. 중복된 지시가 서로 다른 표현으로
유지되면서 모순이 생기거나, 테스트가 동작보다 반복된 문장 자체를 요구하는 곳이 있었습니다.

## 대안과 선택

모든 반복을 일괄 삭제하는 방법과 기존 문장을 모두 유지하는 방법 대신, 규칙마다
별도 역할과 실패 근거를 확인해 정리했습니다. 직접 호출 정책은
[사용자의 명시적 결정](2026-10-24-explicit-skill-invocation.md)으로 유지합니다.
설명 깊이를 먼저 묻지 않는 기본값도 [기존 결정](2026-09-12-explain-before-depth-question.md)을
유지합니다. 제품 지원 호스트를 넓히거나 다른 스킬 호출을 추가하지 않습니다.

| 대상 | 정리한 부분 | 보존할 동작과 근거 |
| --- | --- | --- |
| 한국어 교정 | 중복 보류 표, 진단 모드의 번호 건너뛰기, 가이드의 반복된 말투·장르·보류 절차 | 교정 범위, 사실·의무·가능성·인용 동사, 의도된 문체 보호. [범위·문맥 사례](2026-10-09-slop-skills-quality.md), 기존 37개 사례와 mutation 검사 |
| 한국어 판정 | 진단 분류명 출력 규칙 충돌, 규범적 근거와 출력 인용 혼동, 허용 표기를 불확실성과 섞은 보류 규칙 | 허용되는 표기는 그대로 두고, 실제 불확실성만 보류. 근거 없는 오류 단정 금지 |
| 시각 설명 | 본문 흐름·제한 목록, 시각 가이드의 깊이별 규칙, 출처 정책의 중복 | 여섯 출력 부분, 고정 hop ID, 깊이 우선순위와 같은 턴 설명 |
| 설명 출력 틀 | 주변 반복만 정리하고 본문의 출력 틀 사본은 유지 | [과거 형식 실험](../../maintainers/products/how-it-works/testing.md#live-record-2026-10-01)에서 참조를 읽지 않아 부분을 빠뜨린 실패가 있었음 |
| 호출 평가 | 직접 호출 전용인데 암시적 활성화를 성공으로 기대하던 live fixture | 같은 입력을 비활성 대조군으로 고치고, 스킬 로딩을 관측했다고 주장하는 잘못된 결과 기록을 거부. 선언된 증거의 검증이며 실제 호스트 실행과는 구분 |
| 작성 원칙 | 양성 호출 수와 전체 호출 수 혼동, 이전 자동 호출 정책의 결과를 현재에 일반화한 표현 | 과거 수치와 적용 조건을 분리하고 새 품질은 미측정으로 기록 |

## 구현과 검증 범위

설치 파일을 바꾸므로 두 제품의 `release.toml`, `SKILL.md` 버전과 `CHANGELOG`를
함께 갱신했습니다. 모드·활성화·지원 범위·주요 출력 형식은 유지하는 패치입니다.
공유 릴리스 검사의 중복 버전 문자열은 기준값이나 실제 테스트 입력에서 읽도록 정리했습니다.
계약에 맞는 반례 검사는 유지하고, 내부 설명문이 다른 파일에 똑같이 반복돼야 한다는
검사는 해당 규칙을 소유한 문서와 참조 경로를 확인하도록 바꿨습니다. 새 문장 자체를
고정하는 테스트는 추가하지 않고, 실제 evidence validator의 반례 검사를 추가했습니다.

첫 전체 검사에서는 다운로드 검증 테스트가 Git index의 이전 제품 bytes로 압축 파일을
만들고 수정 중인 작업 트리의 새 버전과 비교해 여섯 실패가 났습니다. 테스트별 임시
`GIT_INDEX_FILE`에 현재 등록 제품만 담아 빌드와 검증의 입력을 맞췄습니다. 실제 index의
전후 SHA-256이 같고 환경 변수가 복원됨을 확인했습니다. 기존 체크섬·버전·신뢰 원본
비교와 압축 변조 검사는 유지했으며, 실패한 테스트 클래스 15개가 통과했습니다.
실제 릴리스 코드는 바꾸지 않았습니다.

제품별 검증 후 전체 검증과 독립 검토를 완료했습니다. 문서 분량 감소는 저장소의
문자·단어 수로 확인할 수 있지만, 모델 토큰 비용·속도·교정 품질의 개선을 직접 뜻하지
않습니다.

## 확인한 결과와 한계

- `python3 scripts/verify.py --skill korean-writing-editor`,
  `python3 scripts/verify.py --skill how-it-works`: 각각 통과.
- 수정 후 `python3 scripts/verify.py`: 저장소 계약 246개, 교정 패키지 11개,
  오프라인 37개 및 mutation 검사, 러너 단위 검사 256개, dry-run,
  설명 제품 검사 64개, Python 컴파일 통과. dry-run은 실제 호출이 아닙니다.
- 암시적 호출 결과 기록의 신규 반례 검사는 수정 전 실패와 수정 후 통과를 확인했습니다.
  교정 evaluator 자체 검사 15개도 통과했습니다.
- 독립 검토에서 핵심 보존 규칙 손실이나 릴리스 fixture 격리 결함을 찾지 못했습니다.
- 활성 Markdown 67개 링크 검사와 `git diff --check` 통과.

공백 기준 단어 수는 기준 커밋 `46c6270`의 파일을 `git show`로 읽고, 현재 파일과
같은 Python `str.split()` 방식으로 비교했습니다. frontmatter를 포함하며 토큰 수가 아닙니다.

이 결과는 제품 계약 검사와 별도로 기록합니다.

새 실시간 호출, 모델 품질 비교, 비용·지연 측정은 하지 않았습니다. 과거 실험의 성공을
이번 수정본의 동작 증거로 옮기지 않습니다. 설명의 기본 깊이, 그림 개수와 비교 표 열 같은
기존 형식 규칙은 이번에 재측정하지 않았고 그대로 두었습니다. 참조를 읽지 않는 모델이
출력 요소를 누락할 가능성도 해소됐다고 주장하지 않습니다.
