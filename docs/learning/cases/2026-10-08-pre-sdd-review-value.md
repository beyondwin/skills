# 구현 전 리뷰 스킬의 추가 절차는 비용만큼 효과가 있었을까?

결정일: 2026-10-08–09. 기록일: 2026-10-09.
관련 작업: pre-sdd-review, 일반 리뷰, 모델 비교, 스킬 작성 원칙.
결과: 실험한 작은 계획에는 일반 리뷰를 권고하고, 반복된 오탐만 줄이는 수정을 적용했습니다.
별도 재검토와 기록의 가치는 관찰했지만 추가 결함 발견은 없었습니다. 사용자는 이후 이 실험을
판단 근거로 pre-sdd-review·sddx·waygent 세 스킬을 선셋했다고 설명했습니다.
근거 성격: 당시 실험 계획·파생 결과·확인한 Git 이력과 현재 대화의 요청 요약입니다.
비공개 대화 원문은 보존하지 않습니다. 이후 선셋의 이유는 2026-10-09 기록 갱신 대화에서
사용자가 직접 보충한 설명으로 구분합니다.

## 시작한 문제

사용자는 pre-sdd-review를 적용한 리뷰가 모델에게 그냥 리뷰를 요청하는 것보다 실제로
도움이 되는지, 시간과 비용을 감수할 가치가 있는지, 개선하거나 사용하지 않는 편이 나은지
근거로 확인하려 했습니다. Grok Build 4.7/high와 Claude CLI Opus 5.5/high의 병렬 비교를
요청했고, Sol 6.1/high를 추가했습니다. Astra/high는 추가 비교 기준으로 사용했습니다.

기대 효과는 더 길고 엄격한 보고서가 아니라 **실제 결함 발견과 유효한 수정 확인**이었습니다.
[사전 실험 계획](../../research/2026-10-pre-sdd-review-eval/method.md)에 탐지 품질, 오탐,
시간·비용, 승인 범위, 변경 파일, 실제 검토 절차를 구분해 적었습니다.

## 당시 조건

- 합성 저장소 4개, 고유한 원인 결함 5개, 정상 계획 대조군을 사용했습니다. 개인 프로젝트
  소스와 정답 기준은 모델 입력에 넣지 않았습니다. 반복 실행은 새로운 독립 결함이 아닙니다.
- pre-sdd-review 6.1.2의 전체 파일을 고정하고 새 저장소·세션, 비활성화한 메모리,
  제한된 병렬 실행을 사용했습니다. 실제 주 에이전트·하위 검토자의 모델과 추론 수준을 확인했습니다.
  [당시 SKILL.md](https://github.com/beyondwin/skills/blob/f4e659b23f2f808ed6cce0e86de4bc1043526e99/skills/pre-sdd-review/SKILL.md)와
  리소스 해시는 보고서에서 식별할 수 있습니다.
- 실행별 한도는 900초였습니다. 초기 실행기 설정 오류와 재시도는 비교 대상과 분리했고,
  판단이 틀린 실행을 원하는 결과가 나올 때까지 재시도하지 않았습니다. 실제 모델 호출은
  사용자가 승인한 비교 범위에서 수행했습니다.
- 당시 공식 지원 호스트인 Codex에서 Sol·Astra를 실행했습니다. Claude·Grok은 탐색 실험이며
  공식 지원을 확대하는 근거로 사용하지 않았습니다.

상세 수치는 [한국어 보고서](../../research/2026-10-pre-sdd-review-eval/README.ko.md),
[영문 보고서](../../research/2026-10-pre-sdd-review-eval/README.md),
[핵심 결과](../../research/2026-10-pre-sdd-review-eval/results.json),
[후속 결과](../../research/2026-10-pre-sdd-review-eval/followups.json)에 한 번만 보관합니다.

## 대안과 선택

- **일반 리뷰:** 실험한 작고 명확한 계획의 기본 권고로 선택했습니다. 별도 조정·검토 절차
  없이도 실제 결함을 찾았고 비용이 낮았습니다.
- **전체 스킬:** 수정 후 별도 검토와 문서 해시가 연결된 기록은 실제로 작동했습니다.
  실험 종료 당시에는 이 성질이 명시적으로 필요한 경우에만 비용을 감수하고 사용하도록 권고했습니다.
- **검토 지침만 제공:** 내용과 전체 절차의 차이를 확인하려고 시험했습니다. 같은 두 사례의
  탐지 결과는 유지했지만 모든 모델에서 일반 리뷰보다 느렸습니다. 새 경량 모드는 만들지 않았습니다.
- **근거가 있는 한 문단 수정:** 기존 지침에서 같은 불필요한 요구가 반복되고 수정 후보의
  새 실행 두 번에서 사라져 채택했습니다. 정상 계획과 실제 결함 탐지가 나빠지지 않는지도 확인했습니다.
- **스킬 전체를 버리거나 크게 축약한다는 일반적 결론:** 작은 사례에서 일반 리뷰부터
  정답을 모두 찾은 실험만으로는 지지할 수 없었습니다. 긴 계획, 여러 계획의 상호작용,
  보안·마이그레이션·동시성은 측정하지 않았습니다. 이후 삭제된 제품의 복원을 결정한 것도 아닙니다.

## 구현 방법

[실행기](../../research/2026-10-pre-sdd-review-eval/harness/run.py)는 같은 합성 입력과
승인·수정 범위 제한 아래 일반 리뷰, 전체 스킬, 지침만 사용하는 조건을 비교했습니다.
탐지, 반복 실행, 문서 수정을 나눠 측정했습니다. 조건 표시를 가린 LLM 채점과 실행 가능한
정답 검사를 사용한 뒤, 지시문·변경 파일·수정 후 검토·기록 상태를 따로 조사했습니다.
채점은 사람 전문가 패널이나 완전히 독립적인 타 공급자 평가가 아니었습니다.

수정 후보는 reviewer protocol에 한 문단만 추가했습니다. 검증 공백을 주장하는 반례는
계획에 이미 적힌 검증을 통과해야 하며, 명시된 입력 범주와 승인된 동작으로 기대값이
결정된다면 구체적인 테스트 데이터를 고르는 일은 구현 세부사항이라는 내용입니다.
실제 검증 누락, 소비자 계약 충돌, 실행에서 빠지는 테스트에 대한 지적은 유지했습니다.

[반영 커밋](https://github.com/beyondwin/skills/commit/7ebdf1af53fdbee4e0628d250e6778102dbc8691)에
실험과 개발 버전 6.1.3이 남아 있습니다. 해당 리비전의
[검토 지침](https://github.com/beyondwin/skills/blob/7ebdf1af53fdbee4e0628d250e6778102dbc8691/skills/pre-sdd-review/references/reviewer-protocol.md)은
실험 후보의 지침 해시와 일치합니다.
[변경 기록](https://github.com/beyondwin/skills/blob/7ebdf1af53fdbee4e0628d250e6778102dbc8691/skills/pre-sdd-review/CHANGELOG.md)은
Unreleased 상태이므로 배포 완료의 증거는 아닙니다. 기록 스키마, 호스트 지원, 기본 모드,
수정 범위는 바꾸지 않았습니다.

## 확인한 결과

- **탐지와 비용:** 주 탐지 비교 48개 중 47개가 완료됐습니다. 완료된 리뷰에서는 양쪽 모두
  실제 결함을 찾았고 추가 발견은 없었습니다. 전체 스킬이 더 오래 걸렸고 Claude의 주 비교
  보고 비용은 약 3.66배였습니다. Claude 스킬 조건에서 중요한 오탐 2건이 나왔으며,
  그중 하나는 정상 계획을 잘못 거절했습니다.
- **수정 후보:** 새 세션으로 기존·수정 지침 두 쌍을 비교했을 때, 구체적 문자열 예시를
  더 요구하는 동일 오탐이 기존 2/2, 수정 후 0/2였습니다. 실제 제품 결정 누락은 계속
  발견했습니다. Sol 두 건을 포함한 별도 정상·실제 결함 검사도 의도한 결과를 유지했습니다.
  특정 스킬 결함을 줄인 결과이며 일반 리뷰보다 우수하다는 증거는 아닙니다.
- **수정과 완료:** 문서 수정 6개 모두 계획 문서만 바꿔 두 원인 결함을 해결했습니다.
  전체 스킬은 별도 검토자로 수정 결과를 확인했습니다. Grok 한 건은 재검토와 READY 기록은
  끝났지만 최종 보고 전달 전에 시간 초과됐습니다. 다른 Grok 시간 초과는 탐지와 판정이
  미완료였습니다. 수정·기록 성공과 최종 응답 완료를 구분해야 했습니다.
- **독립성:** Claude discovery 지시문 3개에 구체적인 결함 단서가 있었습니다. 전체 절차의
  탐지 성공으로는 인정하되 무힌트 독립 재발견으로 보지 않았습니다. Codex는 새 자식 문맥을
  확인했지만 암호화된 지시문 내용은 관찰할 수 없었습니다. Grok 한 건은 위험 범위를 넓게
  해석해 불필요한 추가 검토자를 호출했습니다.
- **재사용:** 커밋하지 않은 소스를 원복하거나 미추적 파일을 삭제하면 재사용 조건의 변경
  목록이 놓칠 수 있는 정적 반례를 확인했습니다. 별도 Sol 실측은 저장소를 다시 확인해
  REVISE를 반환했습니다. 잘못된 READY는 재현하지 못했고 기록 스키마 수정은 별도 과제로 남겼습니다.
- **집계:** 핵심 62개 실행 중 60개 완료, 수정안 8개와 재사용 2개를 합쳐 평가 실행은
  72개입니다. 모델 식별용 호출과 잘못 구성된 초기 실험은 제외했습니다. 하위 모델 호출은
  별도이며 미보고 비용은 미확인으로 남겼습니다. 하위 호출이 포함된 Grok 상위 사용량에
  하위 사용량을 다시 더하지 않았습니다.

당시 보고서는 제품 검사, 별도 staging 체크아웃의 전체 1,286개 테스트·컴파일,
Python 3.14·3.9에서 공급자 없이 실행한 오라클 검사 6개, 문서 검사를 기록합니다.
이는 **실험 당시 리비전의 검증**이며 현재 제품 세 개만 남은 저장소의 새 전체 검사 결과가
아닙니다. 이번 기록 작업은 문서, 저장된 집계, 과거 Git 파일을 확인합니다. 모델 실험을
추가로 실행하거나 오프라인 검사 결과를 모델 품질 증거로 바꾸지 않습니다.

2026-10-09 기록 갱신 검증: 문서 검사 65개, 변경·추가한 Markdown 6개의 로컬 파일·제목
링크 검사, 과거 파일 인용 6개의 Git 객체 확인을 통과했습니다. 기준·수정 지침의 실제
해시와 저장된 실험 집계를 대조했고, diff 공백 검사도 통과했습니다. 새 모델 호출은 없습니다.

## 유지와 종료 판단

실험 종료 당시 선택은 6.1.3의 좁은 오탐 수정과 작은 계획에 대한 일반 리뷰 권고였습니다.
모든 상황에서의 삭제나 새로운 지침 전용 모드를 정당화하지는 않았습니다.

2026-10-09 후속 설명: 사용자는 **이 실험을 통해 판단해 pre-sdd-review, sddx,
waygent 세 스킬을 선셋했다**고 직접 밝혔습니다. 실험 당시의 조건부 유지 권고 이후
최종적으로 내린 종료 판단이며, 그 이유와 실제 삭제는
[삭제 사례](2026-10-09-retire-workflow-skills.md)에 연결합니다. 실험이 직접 검증한
제품·사례의 범위는 유지하면서, 그 결과를 바탕으로 내린 사용자의 선택을 기록합니다.

사용자는 이전 모델에는 이런 하네스가 효과적이었으나 최신 모델의 성능이 발달하면서
필요성이 줄어든 것 같다고 설명했습니다. 이는 과거 사용 경험과 현재 결과를 연결한
사용자의 해석이며, 선셋 판단의 맥락입니다. 이번 비교는 과거·최신 모델 간의 시간에
따른 성능 변화나 그 원인을 직접 측정하지 않았습니다.

합성 입력, 실행기, 파생 채점 결과, 보고서, 과거 구현 링크는 보존합니다. 제공업체 기록
원본, 인증 정보, 전체 응답, 개인 원자료는 넣지 않습니다. 더 넓은 작업의 효용과 이후
제품 결함 예방 효과는 미측정입니다. 이를 알아보려면 같은 다섯 결함의 반복보다 새로운
조건이 필요합니다. 제품 복원이나 추가 실측은 이번 기록 갱신에 포함하지 않습니다.

## 다음에 쓸 배움

제한된 관찰에서 얻은 해석입니다. 절차를 추가하기 전에 어떤 성과를 얻어야 하는지 정하고
충분히 유능한 일반 리뷰와 비교합니다. 추적 기록은 추가 결함 발견 없이도 가치가 있지만
두 주장은 구분해야 합니다. [절차의 효용](../insights.md#추가-절차에는-구체적인-효용이-필요하다)을 참고합니다.

실제 오탐은 반례가 계획된 검증을 통과하는지 확인할 필요를 보여 줬습니다. 새 문맥만으로
무힌트 검토를 입증할 수 없고, 프로세스 종료 코드만으로 모든 단계의 성공 여부를 설명할
수도 없었습니다. [검증 반례](../insights.md#반례는-이미-정한-검증-조건을-지켜야-한다),
[독립성](../insights.md#새-문맥만으로-독립적인-발견을-입증할-수-없다),
[완료 단계 구분](../insights.md#작업-성공과-최종-보고-전달을-구분한다)을 참고합니다.

수정 후보는 SKILL.md를 그대로 두고 참조 지침을 바꿨습니다. 이는 이미 반영된
[리소스 고정 원칙](../../maintainers/repository/skill-practices.md#measuring-a-change)의
근거가 됐습니다. 진입 파일만 보지 말고 변경된 참조 파일이나 전체 파일 목록의 해시를 확인합니다.
