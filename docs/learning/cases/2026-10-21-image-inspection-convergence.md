# 이미지 검수는 언제 충분한가?

결정일·기록일: 2026-10-21. 관련 작업: image-workbench 2.1.2.
근거 성격: 실제 Grok CLI 실행 관찰과 사용자 요청의 요약. 생성 이미지와 제공업체
응답 원본은 로컬 평가 폴더에만 보관하며 저장소에는 넣지 않습니다.

## 시작한 문제

2.1.1은 파일 검사와 이미지 열람 뒤 탁자가 잘린 것을 지적하고도 픽셀 분석을
추가했습니다. Pillow 부재, 디코더 탐색, FFmpeg 파이프 오류, 임시 분석 스크립트
수정으로 이어져 18턴 상한에서 최종 보고 없이 종료했습니다. 같은 요청의 일반
경로는 6턴에 종료했지만 같은 잘림을 지적하지 않았습니다. 각 1회 관찰이므로
일반적인 품질·속도 차이를 뜻하지 않습니다.

## 대안과 선택

검수를 없애거나 모든 분석에 고정 도구 횟수를 부여하는 대신, 이미 충분한 증거와
미해결 수치 조건을 구분했습니다. 명확한 시각 결함은 바로 실패로 판정하고,
합격 여부를 바꿀 미해결 조건에만 추가 측정을 사용합니다. 필요한 측정을 할 수
없으면 미확인 조건을 밝히고 hold로 보고합니다. 정상 이미지의 수용과 실제로
정확한 색·크롭 측정이 필요한 요청은 보존해야 합니다.

## 구현 방법

[SKILL.md](../../../skills/image-workbench/SKILL.md)의 Inspect And Evaluate와
Iterate And Stop을 수정했습니다. 기존 파일 검사·시각 검수·수정 권한은 유지하고,
검사기 소스는 실행 오류 진단이나 수정 시에만 읽도록 했습니다.
[rubric](../../../skills/image-workbench/references/quality-rubric.md)은 실패와
미확인을 구분하며 같은 종료 규칙을 참조합니다. 출력 상태나 활성화 범위는 바꾸지
않는 호환 수정이므로 PATCH 2.1.2를 사용합니다.

## 사전 판정 기준

- 같은 18턴 한도에서 새 이미지 1회 생성, 프로젝트 파일 저장, 검사기 실행,
  이미지 열람, 실제 결과에 맞는 최종 판정까지 end_turn으로 완료해야 합니다.
- 기존 잘림 이미지 감사는 결함을 발견하고 추가 이미지·픽셀 분석 코드 없이 완료해야 합니다.
- 같은 이미지에서 탁자 크롭을 명시적으로 허용한 대조 요청은 크롭만을 이유로 거절하면 안 됩니다.
- 명시적 brief와 가벼운 일회성 그림 경로 질문에서는 이미지 호출·파일 변경이 없어야 합니다.
- 전체 스킬 파일 목록·해시를 실행 전 고정합니다. 기존 사례는 회귀 사례이며 unseen holdout이 아닙니다.

## 확인한 결과

Grok CLI 1.0.62, 실행 기록상 grok-4.7-build에서 다음 결과를 확인했습니다.

| 실행 | 턴 | 도구 호출 | 결과 |
| --- | --- | --- | --- |
| 기존 2.1.1 생성 | 18 | 23 | max_turn_requests, 최종 보고 없음 |
| 수정본 새 생성 | 8 | 12 | end_turn, 이미지 1장 저장·파일 검사·열람 뒤 잘림을 근거로 hold |
| 기존 잘림 이미지 감사 | 4 | 6 | end_turn, 전체 표시 조건 위반을 거절 |
| 크롭 허용 대조 감사 | 4 | 6 | end_turn, 허용된 크롭을 이유로 거절하지 않고 수용 |
| 명시적 brief | 3 | 3 | end_turn, 정확한 제목·버튼을 native로 분리, 생성·파일 변경 없음 |
| 일회성 그림 경로 질문 | 2 | 2 | end_turn, 프로젝트 절차를 실행하지 않음, 생성·파일 변경 없음 |

새 생성 결과도 탁자 하단이 잘렸습니다. 성공한 것은 이미지 품질 개선이 아니라,
문제를 확인한 뒤 추가 픽셀 분석 없이 정확한 최종 보고를 전달한 것입니다.
감사 입력의 SHA-256은 전후 동일했고, 읽기 전용 디렉터리에 새 파일은 없었습니다.
일회성 그림 경로 질문에서는 스킬의 경계를 읽었지만 ImageSpec·프로젝트 검사·복사는
실행하지 않았습니다. 따라서 스킬 텍스트를 전혀 읽지 않았다는 증거는 아닙니다.

실제 세션 식별자와 현재 본문 바인딩은
[스모크 기록](../../../tests/products/image-workbench/live/smoke-record.json)에 있습니다.
원래 실패 세션은 `01a15ce2-b688-7243-89f9-d6b843dd1a84`입니다. 전체 리소스의
변경 전후 해시와 원본 로그는 로컬 평가 폴더에만 있어, 저장소만으로 원본 실행을
재채점할 수 없다는 한계가 있습니다. 실행 전후 설치 리소스 해시 일치를 확인했습니다.

오프라인 evaluator 자체 검사 32개, 계약 사례 32개와 변이 검사 17개를 통과했습니다.
일반 skill-creator 검증기는 기존 `compatibility` frontmatter를 전후 모두 거절합니다.
저장소 자체 계약에서는 필수 필드이므로 이 작업에서 제거하지 않았습니다.
원본 체크아웃의 통합 검사 진입은 gitignored 퇴역 제품 폴더 때문에 막혔으며,
기존 폴더는 보존하고 추적 파일의 현재 내용을 복사한 디렉터리에 패키징 검사용
Git 인덱스를 초기화했습니다. 그 복사본의 `python3 scripts/verify.py`는 종료 코드
0으로 통과했습니다. 단위 테스트 642개, 제품 계약 사례·변이 검사, 컴파일을 포함하며
실제 공급자 호출은 없는 검사입니다. 최초 복사본 검사의 Git 인덱스 부재와 버전
기대값 두 곳의 불일치를 해결한 뒤 통과한 결과입니다.

## 유지와 종료 판단

사전 정의한 회귀 조건에서 검수 종료 문제가 재발하지 않았고, 크롭 허용 대조의
정상 수용도 유지되어 2.1.2 수정안을 유지합니다. 버전은 개발 대상이며 배포·태그·푸시는
하지 않았습니다. 한 번의 새 생성과 기존 이미지 대조이므로 통계적 속도 개선,
일반적인 미적 품질, 정확한 수치 측정, 편집 보존, Codex 실동작은 입증하지 않습니다.

## 다음에 쓸 배움

이 사례에서는 이미 보이는 실패를 다시 수치로 증명하는 분석이 종료를 늦췄습니다.
검사를 생략하는 대신 어떤 미해결 조건이 판정을 바꾸는지 확인하는 좁은 종료 기준이
도움이 됐습니다. 다른 작업에 보편적인 도구 횟수 제한을 적용할 근거는 아닙니다.
