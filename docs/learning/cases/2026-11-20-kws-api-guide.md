# API 연동 안내 문서를 만드는 일을 스킬로 만들까?

결정일·기록일: 2026-11-20.
관련 작업: kws-api-guide 1.0.0 (미배포).
결과: 저장소 소유자 결정으로 세 번째 제품 추가. 오프라인 계약 검사, 전체 저장소 검증, 화면
없는 실제 실행 세 번(두 번째는 페이지 문장 규칙, 세 번째는 보고 언어 시험). 아티팩트 게시와 읽는 사람의 평가는
미측정.
근거 성격: 사용자가 비공개 서버 API 안내 문서 하나를 Claude 와 함께 만들고 서버 코드와
대조해 고친 실제 작업 한 건. 그 문서와 서버의 내용은 이 저장소에 싣지 않습니다.

## 시작한 문제

새로 생기거나 바뀐 API 를 다른 팀 개발자(앱, 웹, 서버)가 붙이려면 경로, 필드, 상태,
오류, 여러 단계 흐름을 한곳에서 정확하게 봐야 합니다. 사용자는 이런 안내 페이지를 한 번
만들었고, 같은 수준의 페이지를 다른 API 에도 반복해 만들 수 있기를 바랐습니다.

## 대안과 선택

| 대안 | 판단 |
| --- | --- |
| 그 API 의 계약을 담은 연동 스킬(호출하는 쪽 저장소에 둠) | 처음 제안했으나 사용자가 바로잡음. 원한 것은 특정 API 지식이 아니라 문서를 만드는 방법 |
| 문서를 만드는 범용 스킬(이 저장소) | 선택. 회사 내용 없이 절차, 확인 항목, 페이지 틀만 담음 |

선택한 스킬의 핵심:

- 서버 사실은 기록한 커밋의 코드에서 읽고, 계약 파일은 찾아갈 지도로만 씁니다.
- 페이지 차례와 카드 차례(요청, 응답, 오류, 처리)를 고정하고 디자인 틀을 참조 파일로 둡니다.
- 호출하는 쪽 할 일 표는 선택이고 동작 수준으로만 씁니다. 사용자가 실제 작업 중
  "너무 코드단위로 디테일하게 하는것보다 앱개발자가 우리꺼 잘붙일수잇도록 우리꺼 정보가
  정확한게 중요해"라고 바로잡은 데서 왔습니다.
- 공개 전 확인 항목과 Gotchas 는 스킬을 만들기 전, 손으로 쓴 안내 문서를 서버 코드와
  대조하며 실제로 틀렸던 것만 적었습니다(전부/만/같음 같은
  단정이 틀림, 같은 이름 필드의 뜻이 응답마다 다름, 부록 모델과 표의 null 불일치, 서버가
  알 수 없는 것을 아는 것처럼 쓴 재발급 안내).
- 호스트는 Claude Code 하나입니다. 결과를 Artifact 도구로 올리기 때문입니다.

CONTRIBUTING 의 "새 스킬은 기본적으로 받지 않는다"는 외부 기여 규칙으로 두고, 이번 추가는
저장소 소유자의 결정으로 기록합니다.

## 확인한 결과와 한계

- 제품 계약 시험 10개: 머리말, 참조 파일 존재, 페이지 차례와 카드 차례, 확인 항목,
  틀이 지어낸 API 만 쓰는지.
- `python3 scripts/verify.py` 전체 통과(결과는 이 브랜치의 마지막 실행 기준).
- 공개 저장소라 새 파일 전체에서 회사, 서버, 제품 이름과 원래 문서의 문자열을 검색해
  나오지 않음을 확인했습니다.
- 같은 날 화면 없는 Claude Code(`claude -p`, opus)로 다른 API 하나(그날 추가된 앱 메인 화면
  API, 앱 저장소 포함)에 한 번 돌렸습니다. 46번 도구 호출, 약 11분. 스킬을 찾아 단계대로
  돌았고, 계약 파일과 코드가 다른 곳 넷을 보고했습니다.
- 그 실행이 찾은 인증 오류 코드 하나(역할 미선택 403)는 실제로 나지 않는 코드였고, 같은
  잘못이 처음 손으로 고친 안내 문서에도 있어 그 문서를 고쳤습니다. 이 실패를 Gotchas 와
  확인 항목에 넣었습니다.
- 화면 없는 세션에는 Artifact 도구가 없어 HTML 파일로만 남았습니다. 이 경우를 SKILL.md 에
  넣었습니다. 아티팩트 게시, 서버 담당자의 전체 검토는 미측정입니다. 기록은
  [테스트 문서](../../maintainers/products/kws-api-guide/testing.md)에 있습니다.

## 이름 변경 (2026-11-20)

- 소유자 요청으로 배포 전에 `api-guide` 를 `kws-api-guide` 로 바꿨습니다. 호출, 경로, 태그
  접두어, 검증 단계 이름을 함께 바꿨고 옛 이름은 남기지 않았습니다. 버전은 배포 전이라
  1.0.0 그대로입니다. 이름을 바꾼 이유는 기록되지 않았습니다.

## 페이지 문장 다듬기 (2026-11-20)

사용자 요청: 결과물을 한국어 글쓰기, AI 티 줄이기, 규칙 단순화로 더 잘 읽히게.

대안:

| 대안 | 판단 |
| --- | --- |
| 일반적인 한국어 글쓰기 금지어 목록(번역투, 꾸밈말) | 버림. 첫 실행 페이지에서 번역투 0건, 꾸밈말 0건이라 고칠 대상이 없음 |
| 다 쓴 뒤 `korean-writing-editor` 로 한 번 더 다듬기 | 버림. 직접 호출 전용이고 설치에 기대며, 다시 쓰다 서버 사실이 틀어질 수 있음 |
| 첫 실행 페이지에서 실제로 나온 패턴만 규칙으로(`references/writing.md`) | 선택 |

첫 실행 페이지(비공개, 수치만 기록)에서 센 것: 세 문장 이상인 표 칸 11개(82칸 중), 괄호
24개, 표 칸의 한다체 6개, 스킬 용어 직역(봉투, 부른 사람) 6개, "수 있습니다" 4개, 머리글
4문장, 문장 192개, 한글 2,853자. 공통 규칙 표는 10행 한 덩어리였고, 이를 "코드에서 처리"와
"형식" 두 표로 나눴습니다.

판정 규칙(실행 전에 정함). 같은 범위로 바뀐 스킬을 한 번 돌려 비교합니다(n=1 시험).

- 사실 회귀가 없어야 합니다: 첫 페이지의 오류 코드 6개와 경로(목록은 저장소 밖에 둠)가
  남고, 손으로
  확인한 세 주장(나지 않는 403, 두 종류 항목이 함께 세는 limit, 공통 형식이 아닌 500)이
  유지됩니다. 하나라도 빠지면 실패이고 규칙을 되돌립니다.
- 읽기 지표: 세 문장 이상 표 칸 3개 이하, 괄호 12개 이하, 표 칸 한다체 0, 스킬 용어 직역 0.
  셋 이상 맞으면 유지, 아니면 규칙을 다시 봅니다.
- 한 번 실행이라 모델 편차와 구분하지 못합니다. 결과는 시험 결과로만 적습니다.

결과(같은 날, 화면 없는 Claude Code, opus high, 1회):

- 비교한 범위에서 사실 회귀 없음. 경로와 오류 코드 집합(28개), 필드 이름(21개)이 첫 실행과
  같았고, 손으로 확인한 세 주장과 범위, 기본값, 정렬, 날짜 규칙 몇 가지도 남았습니다. 페이지
  전체를 서버 코드와 다시 대조하지는 않았습니다. 관리자 역할 403 코드는 두 페이지 모두 앱
  토큰으로는 나지 않는다고 적었고, 첫 페이지는 오류 표의 한 행으로, 새 페이지는 표 밖 설명으로
  적었습니다.
- 서버 저장소의 문체 규칙 파일이 두 실행 모두에 같이 실렸습니다. 이 파일은 장식 기호를 막지만
  ASCII 괄호는 막지 않으므로, 괄호가 줄어든 것을 그 파일 탓으로 보지 않았습니다.
- 읽기 지표 네 개 모두 기준 통과: 세 문장 이상 표 칸 11 → 0, 괄호 24 → 0, 표 칸 한다체 → 0
  (읽어서 확인, 계수기의 오탐 몇 개 포함), 스킬 용어 직역 6 → 0. "수 있습니다" 4 → 0, 머리글
  4 → 3문장. 판정 규칙대로 규칙을 유지합니다.
- 보고는 한국어 요청에 영어로 왔습니다(첫 실행은 한국어). 원인은 모릅니다.
- 한계: 한 번 실행을 이전 한 번과 비교했습니다. 모델 편차와 규칙 효과를 가르지 못하고,
  읽는 사람(앱 개발자)의 평가는 받지 않았습니다. 기록:
  [테스트 문서](../../maintainers/products/kws-api-guide/testing.md).

## 보고 언어 (2026-11-20)

- 두 번째 실행은 한국어 요청에 페이지만 한국어였고, 진행 안내와 마지막 보고는 처음부터
  영어였습니다. 두 실행이 읽은 지시는 같았고(같은 서버 규칙 파일, 같은 사용자 설정), 영어를
  요구한 지시는 없었습니다. 원인은 모릅니다. 스킬 본문이 영어인 점이 끌었을 수 있다고만
  봤습니다.
- 대응: 입력의 language 기본값을 "사용자 언어"에서 "호출 문장의 언어, 페이지·진행 안내·보고
  모두"로 바꾸고 Report 절도 같게 맞췄습니다. Gotchas 에 이 실패를 넣었습니다.
- 확인 실행 1회(같은 범위와 프롬프트): 마지막 보고 한국어, 진행 안내 11개 중 10개 한국어
  (실패한 스크립트 수정 직후 한 줄만 영어). 읽기 지표도 두 번째 실행과 비슷하게 낮았습니다
  (세 문장 이상 표 칸 1, 괄호 3, 스킬 용어 직역 0). 관련 다시 처리 API 언급 하나가 빠졌습니다.
- 한계: 고친 뒤 한 번만 봤으므로, 영어 보고가 다시 나지 않는다고는 말할 수 없습니다.
