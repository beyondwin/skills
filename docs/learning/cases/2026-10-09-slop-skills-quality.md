# AI 티를 줄이는 네 스킬에서 무엇을 가져올까?

검토일·기록일: 2026-10-09.
관련 작업: 외부 스킬 세 후보 검토, 미확인 스킬 하나의 조사, korean-writing-editor 2.0.8.
결과: 기존 편집기에 수정 범위와 문맥 판단을 명시하고 반례 검증을 보강했습니다.
새 스킬 설치·제품 추가·모델 호출·배포는 하지 않았습니다.
근거 성격: 공개 소스, 공급자 없는 실행, 현재 제품 계약 비교입니다.
실제 모델 출력의 전후 비교와 사람의 읽기 품질은 측정하지 않았습니다.

## 시작한 문제

사용자는 [Threads 글](https://www.threads.com/@homebodify/post/DeOq3GIgGLf)에 나온
네 스킬을 실제로 검토하고, 이 저장소의 관련 스킬을 개선하며, 소개 내용을 더 깊게
분석해 달라고 요청했습니다. 여러 관점에서 품질을 확인하는 것이 목적입니다.

평가를 나눈 기준은 작업 적합성, 의미·말투 보존, 과도한 수정과 오탐, 실제 실행 경로,
검사 범위, 비용·저장·유지 부담, 현재 저장소 대비 추가 가치입니다. 하나의 점수로
합치지 않았습니다. 코드 린터의 규칙 준수와 글의 품질을 같은 척도로 비교할 수 없습니다.

## 당시 조건과 원본 식별의 한계

글에서 확인한 것은 이름과 설명입니다. 읽힌 작성자 글 네 개에는 저장소 링크가 없어,
아래는 이름과 작동 방식이 일치하는 공개 후보입니다. 작성자가 설치한 정확한 포크나
리비전까지 확인했다는 뜻은 아닙니다. 세 후보의 MIT 라이선스를 각각 읽었습니다.

마지막 스킬은 정확한 이름의 웹 검색과 GitHub 코드 검색에서 구현을 찾지 못했습니다.
원본 링크를 요청했습니다. 검색 실패를 비공개·삭제·미존재의 증거로 보지 않습니다.

현재 저장소는 [제품 목록](../../../products.toml)의 세 제품을 유지합니다. 과거
[작업 흐름 스킬 선셋](2026-10-09-retire-workflow-skills.md)과
[한국어 글쓰기 연구](2026-10-09-korean-writing-policy.md)를 읽었지만, 그때의
평가를 이번 후보의 성능으로 재사용하지 않았습니다. 새 제품 추가, 전역 설정 변경,
유료 실험까지 승인받은 것으로 확대하지 않았습니다.

## 스킬별 판단

### no-ai-slop: 가벼운 편집 지침, 강한 금칙어는 주의

[지침](https://github.com/petergyang/no-ai-slop/blob/000650b156983f5159695b441477f4e63b25dc85/skills/no-ai-slop/SKILL.md)은
최소 수정, 목소리 보존, 진단과 편집의 분리를 명시합니다. 진단을 AI 저자 판별이나
점수로 제시하지 않는 점도 좋습니다. 짧은 영문 초안을 다듬는 작업에는 직접적입니다.

반면 조건 없는 단어 금지와 일부 문장 형태 제거 규칙은 문맥을 잃을 수 있습니다.
예를 들어 회귀 분석의 `leverage`는 쓸모없는 장식어가 아닙니다. 대조 구문에서
부정하는 대상을 지우면 전달하는 구분도 사라집니다. 사실을 추가하지 말라는 규칙과
근거가 주어지지 않은 구체적 수치를 넣는 수정 예시 사이에도 긴장이 있습니다.
이것은 지침에서 확인한 위험이며, 이번에 모델이 실제로 그 잘못을 했다는 관찰은 아닙니다.

[eval.md](https://github.com/petergyang/no-ai-slop/blob/000650b156983f5159695b441477f4e63b25dc85/skills/no-ai-slop/eval.md)는
모델이 자기 출력을 점검하는 체크리스트입니다. 독립 채점·비교 실험·반복 종료 보장은
아닙니다. 패키지 빌드는 성공했지만 그 성공으로 글의 품질을 평가할 수 없습니다.
현재 편집기에는 최소 수정과 말투 보존이 이미 있어, 금칙어 목록을 수입할 이유는 약합니다.

### humanize-korean: 검사 가능한 작업 흐름, 의미 검증의 공백

[Codex 지침](https://github.com/epoko77-ai/im-not-ai/blob/2f3d943d08056b612a92e12bfb72ea94dd2acd18/codex/skills/humanize-korean/SKILL.md)은
소개 글의 40여 개보다 늘어난 85개 패턴을 표기합니다. light·standard·heavy 경로,
부분 수정, 변경률 제한, 재조립, 최종 검토를 구분합니다. 독립 역할과 파일을 사용해
진행 상태를 추적할 수 있지만, 원문·중간 결과를 작업 폴더에 저장하고 복수의 모델
작업을 수행할 수 있습니다. 짧은 교정에 쓰는 현재 편집기보다 운영 부담이 큽니다.

[게이트](https://github.com/epoko77-ai/im-not-ai/blob/2f3d943d08056b612a92e12bfb72ea94dd2acd18/scripts/verify_gates.py)의
기존 테스트 40개는 모두 통과했습니다. 별도로 만든 합성 사례에서는 다음을 확인했습니다.

| 입력에 가한 변경 | 실제 결과 | 해석 |
| --- | --- | --- |
| 변경 없음 | exit 0, 변경률 0% | 정상 대조 사례 |
| 참가자 `40명`을 삭제 | exit 0, 변경률 12.12%, 숫자 소실 목록에 `40` | 소실은 보고하지만 실패 조건은 아님 |
| `원본이 아니다`를 `원본이다`로 변경 | exit 0, 변경률 3.45%, 의미 관련 검출 없음 | 적은 문자 변경으로 핵심 의미가 뒤집혀도 통과 |

게이트 자체가 모든 의미를 증명한다고 가정하면 안 됩니다. 정상 대조 1개와 오류 후보
2개로 실제 윤문 모델의 실패율을 추정할 수도 없습니다. 전체 게이트·통계·원문 저장
파이프라인은 가져오지 않고, 수정 대상을 한정하는 원칙을 현재 계약 안에서 명확히 했습니다.

### anti-slop: 특정 팀의 코드 규약에는 유용, 일반 품질 점수는 아님

[규칙](https://github.com/dmmulroy/anti-slop/blob/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b/src/rules/no-array-filter-map.ts)은
AST와 스코프로 판정합니다. 반복되는 코드 규약을 모델의 기억에 맡기지 않고 검사할
수 있다는 장점이 있습니다. 자체 `pnpm check`는 린트, 테스트 파일 24개, 타입 검사,
설치용 복사본 일치 검사를 모두 통과했습니다.

독립적으로 작성한 다섯 사례에서는 직접 배열 타입을 붙인 파이프라인만 잡고,
타입 없는 매개변수와 타입 별칭은 놓치는 경계를 확인했습니다. `unknown`을 받아
타입을 검사하고 숫자를 반환하거나 예외를 던지는 올바른 파서도 규칙상 거부했고,
타입 술어 함수는 허용했습니다. 명시된 코드 취향과 프로그램의 옳고 그름은 다릅니다.

eager 배열을 lazy iterator로 바꾸는 실행 반례도 확인했습니다.

- 콜백 순서: `filter1 → filter2 → map1 → map2`가
  `filter1 → map1 → filter2 → map2`로 달라졌습니다.
- 희소 배열: 비어 있는 슬롯을 건너뛰던 결과에 `undefined`가 추가됐습니다.

원본도 이런 한계 때문에 자동 수정을 제공하지 않습니다. 위 결과는 자동 수정 결함을
발견했다는 뜻이 아니라, 그 주의가 실제로 필요함을 보여 줍니다. 소개 글의 비용·실수
없다는 표현은 좁혀 읽어야 합니다. 모델 토큰 호출은 없지만 CI 실행·규칙 관리 비용과
오탐·미탐 가능성은 남습니다. Python과 Markdown 중심인 이 저장소에 일괄 도입하지 않았습니다.

### lagging-concepts: 원칙은 검토 가능, 제품 품질은 판단 보류

오래된 가정을 재확인한다는 목적은 타당합니다. 하지만 언제 검토하고, 어떤 근거로
가정을 버리고, 반복을 언제 끝내는지는 원본 없이 알 수 없습니다. 현재 작업에서도
과거 제품 목록을 믿지 않고 `products.toml`과 현행 계약을 확인했습니다. 이 일반적인
행동만으로 미확인 스킬의 추가 효과를 증명하거나 새 실행 하네스를 만들지는 않았습니다.

## 대안과 선택

검토한 선택은 네 스킬을 함께 설치하기, 공통 금칙어·린트를 추가하기, 기존 제품의
경계만 보강하기, 아무것도 바꾸지 않기였습니다. 세 번째를 선택했습니다.
확인된 중복은 유지하고, 금칙어에 맞추려다 의미를 손상하거나 요청 범위를 넘는 위험을
짧은 규칙과 검사 사례로 다룹니다. 이 선택은 유지 부담과 계약 정합에 관한 판단이며,
다른 스킬보다 글쓰기 성능이 높다는 측정 결과는 아닙니다.

## 구현 방법

[korean-writing-editor](../../../skills/korean-writing-editor/SKILL.md)를 2.0.8로 변경했습니다.

- 지정 문단 밖은 오류가 있어도 수정하지 않는다고 명시했습니다.
- 영어 전문 용어·대조·반복 패턴만으로 잘못을 단정하지 않도록 했습니다.
- [편집 가이드](../../../skills/korean-writing-editor/references/editorial-guide.md),
  영문·한국어 README, 계약, 버전·CHANGELOG를 맞췄습니다.
- 오프라인 사례 2개와 잘못된 후보 7개를 추가했습니다. 선택한 문단의 오류를
  그대로 두기, 범위 밖 오류까지 고치기, 날짜 변경, 문맥 삭제, 불필요한 용어·대조·말투
  변경을 거부합니다.
- 기존 live 대조 사례 하나를 확장하고 해시와 단위 검사를 갱신했습니다.
  총 14사례·17반복과 호출 예산은 유지했습니다. 실행 승인은 새로 부여하지 않습니다.

제품 추가나 지원 호스트 변경은 없습니다. `image-workbench`와 `how-it-works`는
이미지·설명용 계약이므로 이번 글 편집·JS 린트 원칙을 억지로 추가하지 않았습니다.
사용자가 앞서 수정한 문서 4개도 그대로 보존했습니다.

## 확인한 결과와 한계

재현 방법·버전·원시 집계는 [연구 기록](../../research/2026-10-slop-skill-audit/README.md)과
[공급자 없는 프로브](../../research/2026-10-slop-skill-audit/probe.py)에 있습니다.

제품 전용 검증은 현재 변경분을 복사한 격리 Git 복제본에서 통과했습니다.
제품 계약 24개, 패키지 검사 11개, 오프라인 사례 37개와 변이 검사, 평가기 단위 검사
256개, dry-run, Python 컴파일입니다. 실제 모델 호출은 0회입니다.

원래 작업 폴더에서는 이전에 삭제한 제품의 무시된 Python 캐시 디렉터리 때문에
등록 목록 검사가 먼저 실패했습니다. 이를 삭제하지 않고 격리 복제본을 사용했습니다.
별도로 macOS 기본 Python 3.9.6에서 기존 평가기 단위 테스트를 실행했을 때는
기존 `datetime.UTC` 사용 때문에 오류 108개가 났습니다. 문서 계약 불일치 1개는
이번 변경에서 고친 뒤, 저장소의 `python3` 3.14.7 경로에서 256개가 통과했습니다.
이는 Python 3.9에서 전체 평가기가 지원된다는 증거가 아닙니다. 새 프로브는 3.9에서 실행했습니다.

저장소 전체 `python3 scripts/verify.py`도 같은 변경분을 담은 격리 스냅샷에서
통과했습니다. 단위 테스트 총 642개, 한국어 오프라인 사례 37개, 이미지 계약 사례
32개와 각 변이 검사, dry-run, 컴파일을 포함합니다. 배포 테스트가 Git의 파일을
읽기 때문에 임시 복제본에서만 검증용 커밋을 만들었습니다. 원래 저장소에는
커밋·푸시를 하지 않았습니다. 현재 작업 폴더의 과거 캐시 문제는 남아 있습니다.

일반 `skill-creator`의 `quick_validate.py`는 저장소가 요구하는 `compatibility`
키를 허용하지 않아 실패했습니다. 변경 전 HEAD에서도 같은 실패를 재현했습니다.
이 키를 삭제하지 않고 저장소 전용 제품 계약·패키지 검사로 확인했습니다.

## 유지와 종료 판단

이번 결과는 원본 검토, 실행 가능한 반례, 범위를 좁힌 제품 개선입니다.
새 모델 품질 비교, 원본 미확인 스킬의 평가, 커밋·설치·배포까지 완료했다고 말하지 않습니다.
문장 품질 개선을 주장하려면 같은 원문·모델·조건에서 변경 전후를 비교하고, 보지 않은
사례와 사람의 선호·의미 보존을 별도로 평가해야 합니다.

현재의 해석: 패턴 목록은 검토할 위치를 찾는 데 쓸 수 있지만 교정의 정답이 아닙니다.
정상 문장을 그대로 두는 대조 사례와 검사기가 놓치는 실패를 함께 남기는 쪽이
단순히 규칙 수를 늘리는 것보다 이번 저장소의 목적에 맞습니다.
