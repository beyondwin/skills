# 다시 쓰기 전에 확인할 인사이트

연결된 사례를 바탕으로 2026-10-09에 정리했습니다. 조건이 있는 교훈이며 새로운
제품 계약이 아닙니다. 각 항목은 당시 근거와 현재의 해석을 구분합니다.
이번 정리만으로 스킬 작성 원칙에 승격한 항목은 없습니다. 제목은 링크가 유지되도록
안정적으로 관리합니다. 근거가 달라지면 날짜가 있는 한정 설명과 후속 사례를 붙이고,
과거 결정이 무엇에 근거했는지 몰래 바꾸지 않습니다.

## 추가 절차에는 구체적인 효용이 필요하다

- **주장:** 작업 관리 절차를 추가할 때는 비용을 감수할 만큼 구체적인 성과가 있어야 합니다.
  더 엄격한 문구가 올바른 작업까지 중단시킬 수도 있습니다.
- **근거:** [waygent 사례](cases/2026-09-27-light-implementation-workflow.md)에 연결된
  구성 요소 비교와, 더 엄격한 규칙을 기각한 판단 실험입니다.
- **범위:** 해당 실험의 구현 작업과 겨냥했던 실패에 한정됩니다.
  제한된 결과를 종합한 해석이며 보편적인 모델 순위가 아닙니다.
- **예외:** 추가 결함을 찾지 못해도 독립적인 종료 검토나 오래 보관할 추적 기록이 명시적인
  요구일 수 있습니다. 사용자 선호는 별도의 이유이며 실험상의 우위를 뜻하지 않습니다.
- **다음 행동:** 기존 방식과 절차를 추가한 방식을 비교합니다. 기대 효과를 먼저 정하고,
  특히 올바른 작업이 새로 막히는지 등 부작용을 확인합니다.

2026-10-09 후속 근거: [pre-sdd-review 비교 사례](cases/2026-10-08-pre-sdd-review-value.md)는
구현 전 검토에 관한 별도 관찰입니다. 작은 계획의 완료된 실행에서는 일반 리뷰도 실제
결함을 모두 찾았고, 전체 절차는 시간과 중요한 오탐 2건을 추가했습니다. 별도 재검토와
추적 기록은 작동했습니다. 좁은 수정으로 반복 오탐을 줄였지만 일반 리뷰보다 나아졌다는
증거는 아닙니다. 실험 종료 당시에는 필요한 경우에만 절차를 쓰도록 권고했습니다.
이후 사용자는 이 실험을 근거로 세 스킬을 선셋했다고 직접 설명했습니다.
그 최종 선택은 [삭제 사례](cases/2026-10-09-retire-workflow-skills.md)에 보존하며,
측정 범위를 세 제품 모두의 보편적인 성능 판정으로 확대하지 않습니다.

## 모델이 발전하면 보완 절차의 필요성도 다시 판단한다

- **주장:** 과거 모델의 약점을 보완하던 절차는 모델 자체의 능력이 좋아지면 추가 가치가
  줄 수 있습니다. 이전에 효과가 있었다는 사실만으로 계속 유지할 필요가 정해지지는 않습니다.
- **근거:** 2026-10-09 사용자는 이전 모델에서 효과적이던 하네스가 최신 모델에서는
  불필요해진 것 같다고 설명했고, 이번 비교를 근거로 세 스킬을 선셋했습니다.
  [선셋 사례](cases/2026-10-09-retire-workflow-skills.md)와
  [실험 사례](cases/2026-10-08-pre-sdd-review-value.md)에 경험·판단·실측을 구분했습니다.
- **범위:** 사용자의 세 워크플로 스킬 유지 판단과 이번 작은 계획 비교입니다.
  최신 모델의 일반 리뷰가 실제 결함을 찾은 것은 실측이며, 과거 대비 변화와 그 원인에
  대한 설명은 사용자 경험과 해석입니다. 같은 조건의 구형·최신 모델 비교는 하지 않았습니다.
- **예외:** 모델 성능과 별개로 필요한 권한 제한, 외부 시스템 연결, 실행·검증 환경,
  명시적인 감사 기록까지 이번 결과로 불필요하다고 판단하지 않습니다.
- **다음 행동:** 모델을 바꿀 때 기존 절차 없이도 목적을 달성하는지 확인하고, 남는
  효용과 비용을 기준으로 유지·축소·선셋을 결정합니다. 절차 자체의 보존을 목표로 삼지 않습니다.

## 기본값으로 불필요한 질문을 줄일 수 있다

- **주장:** 범위가 정해진 설명에서는 사용자가 바꿀 수 있는 기본값을 알리고 적용해
  가치가 낮은 확인 질문을 줄일 수 있습니다.
- **근거:** [how-it-works 사례](cases/2026-09-12-explain-before-depth-question.md)입니다.
  설계에 대한 해석이며 당시 변경에서는 학습 효과를 측정하지 않았습니다.
- **범위:** 설명할 메커니즘이 이미 정해져 있고 사용자의 명시적 선택을 우선하는 상황에서의
  표현 깊이 선택에 적용합니다.
- **예외:** 주제가 없거나 요구가 충돌하거나 결과에 큰 영향을 주는 선택과 고위험 제약이
  있다면 여전히 확인이 필요할 수 있습니다.
- **다음 행동:** 질문이 답변의 본질을 바꾸는지, 안전하게 할 수 있는 첫 설명만 늦추는지
  구분합니다. 기본값을 택하면 이를 알리고 명시적 선택을 존중합니다.

## 삭제 결정과 실험 결과는 다른 주장이다

- **주장:** 제한된 실험 결과만으로 사용자가 해당 제품을 삭제한 이유를 확정할 수 없습니다.
- **근거:** [삭제 사례](cases/2026-10-09-retire-workflow-skills.md)는 처음에 커밋과 보고서만으로
  이유를 확정하지 않았고, 이후 사용자의 직접 설명으로 실험과 선셋 결정의 연결을 확인했습니다.
- **범위:** 코드, 실험, 커밋 이력으로 의도를 복원하는 작업에 적용합니다.
  초기 자료에 이유가 없었던 것은 그 시점의 복원 한계이며, 이유 자체가 없었다는 증거는 아닙니다.
- **예외:** 의사결정 기록이 실험을 삭제 이유로 직접 인용할 수 있습니다.
  나중의 사용자 설명도 사후 회고임을 표시하면 이유를 보충할 수 있습니다.
- **다음 행동:** 실제 처리 결과와 확인된 이유를 따로 적습니다. 이유를 알 수 없으면
  미확인으로 두고 날짜가 있는 후속 설명을 추가할 수 있게 합니다.

2026-10-09 사용자 설명 반영: 이번 사례의 삭제 이유는 더 이상 미확인이 아닙니다.
사용자가 pre-sdd-review 비교 실험 결과를 근거로 세 스킬 모두를 선셋했다고 명시했습니다.
이는 위 예외에 해당하는 직접적인 이유 보충이며, 초기 기록을 당시부터 알고 있었던
것처럼 바꾸지 않고 설명 시점을 남겼습니다.

## 반례는 이미 정한 검증 조건을 지켜야 한다

- **주장:** 검증 공백 때문에 계획을 고쳐야 한다면, 잘못된 구현이 그 계획에 이미 적힌
  검증을 통과할 수 있음을 보여 줘야 합니다.
- **근거:** [비교 사례](cases/2026-10-08-pre-sdd-review-value.md#확인한-결과)에서
  입력 범주와 기대 동작이 정해졌는데도 구체적 예시를 추가 요구하는 오탐이 반복됐습니다.
  좁은 지침 수정으로 새 비교 두 쌍에서 해당 오탐을 없애고 정상·실제 결함 검사를 유지했습니다.
- **범위:** 이 작은 승인 계획들의 명시적인 검증과 불변 조건입니다. 구체적인 예시를
  더 쓰는 일이 항상 불필요하다는 뜻은 아닙니다.
- **예외:** 실제 검증 누락, 실행에서 빠지는 테스트, 미정인 승인 동작은 여전히 문제입니다.
  설계에 불변 조건이 있다는 사실만으로 계획에 효과적인 테스트가 있다고 간주하지 않습니다.
- **다음 행동:** 계획이 실제로 요구한 검증과 검토자가 있다고 가정한 검증을 구분합니다.
  가능하면 검증을 통과하는 잘못된 구현을 재현합니다.

## 새 문맥만으로 독립적인 발견을 입증할 수 없다

- **주장:** 새 검토자에게도 주 에이전트의 구체적인 결함 단서가 전달될 수 있으므로,
  에이전트 수만으로 독립 재발견을 입증할 수 없습니다.
- **근거:** [절차 조사](../research/2026-10-pre-sdd-review-eval/README.md#default-repair-and-process-value)와
  [사례](cases/2026-10-08-pre-sdd-review-value.md)는 Claude의 지시문 단서 3건과
  전체 절차의 올바른 발견을 구분했습니다. Codex의 지시문 본문은 관찰 불가로 남겼습니다.
- **범위:** 발견의 독립성에 관한 주장입니다. 올바른 근거로 확인된 결함 자체를 무효화하지 않습니다.
- **예외:** 수정 후 확인에는 원래 지적과 수정 diff를 전달해야 합니다. 이는 초기 탐지에
  답을 미리 주는 것과 다릅니다.
- **다음 행동:** 독립성이 중요하면 실제 초기 지시문과 추가 검토자 호출 조건도 확인합니다.
  접근할 수 없는 내용은 미확인으로 남깁니다.

## 작업 성공과 최종 보고 전달을 구분한다

- **주장:** 실제 작업, 수정의 정확성, 별도 확인, 기록 저장, 최종 응답 전달은 서로 다른
  시점에 끝날 수 있습니다. 각각의 결과를 구분해 보존해야 합니다.
- **근거:** [비교 사례](cases/2026-10-08-pre-sdd-review-value.md#확인한-결과)의 Grok
  실행은 계획 수정·새 검토자의 확인·READY 기록을 완료한 뒤 최종 보고 전달 전에 시간 초과됐습니다.
- **범위:** 여러 단계로 구성된 에이전트 실험과 복구 상태의 집계입니다. 미완료 주 에이전트
  실행을 완료된 사용자 응답으로 바꾸어 세는 규칙은 아닙니다.
- **예외:** 다른 Grok 시간 초과는 최종 판정과 기록이 미완료였습니다. 하위 검토자의
  중간 응답으로 빠진 결과를 대신 채워 넣으면 안 됩니다.
- **다음 행동:** 실제 단계별 산출물을 확인합니다. 전체를 완전한 성공이나 유용한 작업이
  전혀 없는 실패로 단순화하지 않고, 최종 전달 실패와 미확인 비용도 명시합니다.

## 아직 확인할 운영 가설

[도입 사례](cases/2026-10-09-preserve-decision-context.md)는 작업 종료 시 짧게
기록하면 다음 작업에 재사용하기 쉬워진다는 가설을 제안합니다. 실제 사용 후 평가해야
하며, 문서가 생겼다는 사실만으로 시간이 절약됐다고 주장하지 않습니다.
