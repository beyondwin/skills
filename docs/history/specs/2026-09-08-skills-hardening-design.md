## 1. 승인 범위와 증거 사용

원래 요청은 저장소 구조와 네 스킬의 결함·개선·사각지대를 전담 에이전트로 병렬 검토하는 것이었다. 사용자는 균형 있는 우선순위와 기존 구조 보강 방향을 승인했다.

이 문서는 승인된 구현 계약이다. 감사 보고서의 문장을 그대로 요구사항으로 승격하지 않는다. 코드에서 확인한 동작, 현재 계약, 반대 증거, 정책 선택을 구분한다. 구현 계획은 별도 문서로 작성한다.

지난 검토의 로컬 baseline은 macOS/Python 3.14.7에서 전체 검증 exit 0, unittest 700개, Korean/image offline 62개였다. 이는 현재 모델 품질·원격 CI·실제 Windows/Linux 실행의 증거가 아니다. 이번 설계 단계에는 모델·API 호출과 설치본 갱신이 없다.

## 2. 유지할 구조와 경계

설치 payload는 skills/<name>/, 제품 검증은 tests/products/<name>/, 관리자 계약은 docs/maintainers/products/<name>/에 둔다. products.toml의 owned_paths가 제품별 작업 경계다. 공통 스크립트와 tests/repository는 통합 담당 한 명이 소유한다.

새 스킬, 범용 프레임워크, 필수 외부 공급자, 텔레메트리, 저장소 분할을 추가하지 않는다. catalog의 불변 두 제품 번들을 자동으로 갱신하지 않는다. 현재 지원 호스트 범위를 넓히지 않는다.

제품 지침과 관리자 계약이 충돌하면 둘 중 편한 문장을 테스트로 고정하지 않는다. 아래에서 제안한 해석을 문서 승인으로 확정한 뒤 대응되는 지침·사례·검사를 함께 고친다.

## 4. 공통 검증·배포·설치 계약

### 4.1 CI 선택과 레지스트리

공통 경로·알 수 없는 경로·diff 계산 실패·빈 변경 목록은 selector 없는 전체 matrix를 선택한다. 명확한 제품 전용 변경만 해당 제품 selector를 사용한다. catalog 전용 변경의 현재 분리는 유지한다.

레지스트리는 최상위 허용 키, 정확한 정수 schema, 제품 필드 타입, 비어 있지 않은 supported_hosts/owned_paths/verify_stages, 목록 중복을 검사한다. 기존 실제 디렉터리·단계 이름·제품 동일성 검사도 유지한다. 빈 단계 목록을 실행하려는 경우 명시적 오류로 끝낸다.

경로 선택 테스트는 이름 목록뿐 아니라 matrix의 selector가 실제로 어떤 단계와 공통 테스트를 실행하는지 확인한다. 선택 결과의 오타나 공통 검사가 없는 성공을 허용하지 않는다.

### 4.2 다운로드 바이트

검증 흐름은 checksum → archive 구조 → 안전한 추출 → 메타데이터 → 신뢰하는 소스 payload hash 비교 → 추출본 smoke 순서다. 네 제품에 동일하게 적용한다.

신뢰 기준은 호출자가 선택한 로컬 checkout의 해당 제품 payload와 버전이다. checksum 자체를 인증 수단으로 표현하지 않는다. 소스/버전이 다르면 다른 신뢰 기준을 추측하지 않고 거부한다. 다른 제품과 catalog의 고정 바이트를 바꾸지 않는다.

### 4.3 설치와 문서 링크

clone 안내는 clone 뒤 작업 디렉터리를 명시한다. 링크 대상이 없으면 생성하고, 이미 같은 소스를 가리키면 변경 없이 성공한다. 실제 디렉터리·다른 링크·깨진 링크는 자동 삭제·교체 없이 명확히 종료한다. 상위 스킬 폴더를 변경하지 않는다.

설치되는 README의 상대 링크는 payload 내부에서 해석 가능해야 한다. 저장소에만 있는 관리자/사용자 문서는 공개 저장소 URL로 연결한다. 링크가 원격에서 현재 응답하는지는 별도 네트워크 증거이며 파일 검사로 주장하지 않는다.

실제 사용자 설치 경로에서 시험하지 않는다. 공백이 있는 임시 경로와 정상/기존/다른/깨진 링크를 사용한다.

## 5. 제품별 제안 계약

### 5.1 Image Workbench

원본 입력과 출력의 동일성은 정규화 경로와 파일 동일성을 함께 확인한다. 같은 파일을 가리키는 상대 경로·절대 경로·symlink·hard link에서는 쓰기 전에 거부한다. 실패 시 입력 바이트는 보존된다. 원본과 무관한 기존 JSON 출력 파일의 현재 갱신 동작은 이번 수정에서 바꾸지 않는다.

PNG의 IHDR CRC, scanline 필터 범위, indexed palette 필수성을 확인한다. JPEG SOS 구조와 WebP의 예약/version 비트 등 파서가 해석하는 구조의 필수 조건도 확인한다. 완전한 비트스트림 디코딩, 시각 품질, 권리 검증을 성공했다고 출력하지 않는다. 기존 파일 사실 필드는 유지하고 README/rubric에 검증 범위를 명확히 적는다.

brief/audit/no-op의 금지된 생성·교체 행동은 expected/candidate 값과 독립적으로 판정한다. fixture 정답과 후보가 함께 틀린 반례도 거부한다.

### 5.2 Korean Writing Editor

기존 LiveCase/Finding 경계와 실행 진입점은 유지한다. R6를 이유로 모듈 추출을 완료 조건으로 추가하지 않는다.

상태 판정은 요구된 차원을 따라간다. 확정된 hard 위반이 있으면 failed, hard 위반은 없지만 의미·귀속·실행 증거가 부족하면 partially_verified다. 양성 정규형으로 필수 차원을 입증한 경우에만 verified다. 문자열 개수로 화자-발언 관계나 문장 의미를 입증하지 않는다.

diagnose에서 수치의 단순 미언급은 hard drift가 아니다. 다른 수치를 원문의 사실로 재진술한 양성 반례는 hard 위반이다. 문맥상 인용·예외 설명인지 결정할 수 없는 자유형 표현은 미측정으로 남긴다. 원문을 다시 쓰도록 요구하지 않는다.

transport 정규화 결과에는 본문과 관측 가능한 도구 이벤트의 근거를 분리한다. 호스트가 이벤트를 제공하지 않거나 관측 범위가 불완전하면 실행 여부는 미측정이다. 정상 최종 답변이 금지된 명령 실행 시도를 상쇄하지 않는다. 스킬 파일 읽기를 곧바로 위반으로 분류하지 않는다.

기존 영수증·예산·설치 preflight·보고서 임대 규칙은 유지한다. 새 판정 의미는 새 runner identity로 식별하고 이전 receipt를 새 판정의 증거로 재사용하지 않는다. 실제 API 호출 없이 합성 transport로 검증한다.

correct와 polish 모두 명백한 국소 문법·규범 오류를 고친다. 의미 선택이 필요한 재구성과 가독성·흐름 개선은 polish에만 둔다. 말투·수치·인용·코드 보존은 두 모드에 모두 적용한다.

### 5.3 How It Works

깊이 우선순위는 명시한 rung → 명시한 깊이 별칭 → 기존 jargon 기본값 → 필요한 경우 한 질문이다. 쉽게/한눈에 등 명시적 쉬움 요청은 jargon보다 우선한다. 숫자 별칭은 깊이 선택으로 명시된 경우에만 해석한다. 주제 속 숫자를 깊이로 오인하지 않는다. 트리거와 debugging/ELI5 제외 경계는 유지한다.

이 정책은 현재 jargon 우선 계약을 바꾸므로 버전의 기본 동작 변경으로 다룬다. 기존 테스트의 기대값을 먼저 바꾸어 새로운 규칙이 원래 계약이었던 것처럼 만들지 않는다.

출력은 현재의 여섯 요소와 동일 hop ID를 유지한다. 허점에서도 기준 Mermaid와 hop 목록을 유지하고, 실패/적용 범위 표는 본문에 둔다. 한국어 템플릿과 배너는 해요체로, 영어 출력은 영어 안내로 통일한다.

안정적인 일반 원리는 불필요한 조회 없이 설명할 수 있다. 시점·관할·불확실성에 의존하는 주장은 호스트 정책과 사용자 제약 안에서 1차 출처로 확인하거나 미확인으로 표시한다. 검증하지 않은 논문·법령 ID를 만들지 않는다. 고위험 비교는 개인 행동 추천을 강제하지 않고 조건별 차이를 설명한다.

과거 smoke는 historical-unbound 증거로 보존한다. 당시 payload/model 값을 추측해 채우지 않는다. 새 기록 형식은 제품 버전·payload hash·모델·클라이언트/실행기·실행일을 갖고, 현재 payload와 연결되지 않으면 현재 빌드 검증을 주장하지 않는다. 지원 대상과 현재 측정 상태를 구분한다.

fence 존재, hop ID 대응, 실제 skill loading, Mermaid 문법, 의미 정확성은 별도 차원이다. 단순 정규식으로 Mermaid 전체 문법을 verified라고 표시하지 않는다. parser/renderer 또는 의미 평가가 실행되지 않았다면 해당 차원은 미측정이다. 필수 런타임이나 새 유료 검증을 추가하지 않는다.

### 5.4 Pre-SDD Review

리뷰어 수, 기존 위험 trigger 목록, 두 문서 수정 범위, 최대 두 repair pass, verdict 규칙은 유지한다. P5를 근거로 복합 trigger 배열이나 새로운 역할을 추가하지 않는다.

저장소 식별·레코드 형태를 바꾸는 다음 정책을 제안한다. 이 부분은 단순 문구 수정이 아닌 명시적인 기록 형식 변경이다.

- 새 기록은 schema 3이며 basename과 별도로 checkout 식별자를 갖는다.
- 식별자는 로컬 evidence home의 비공개 salt와 정규화한 해당 checkout의 Git 디렉터리 위치·checkout root를 함께 입력한 HMAC이다. 원시 절대 경로는 기록하지 않는다. 계획 작성 중 확인한 `git worktree move`는 Git 디렉터리 위치를 유지할 수 있으므로, 아래의 이동 시 새 식별자 조건을 충족하도록 checkout root도 포함한다.
- 별도 clone과 별도 worktree는 다른 식별자다. checkout 이동은 새 식별자로 취급한다.
- salt 생성은 동시 초기화에 안전해야 하며 run별 잠금과 분리한다. 비공개 권한을 유지한다.
- finish는 현재 checkout 식별자가 시작 기록과 같은지 검사한다. basename은 표시와 이름 필터용이며 chain 동일성의 키가 아니다.
- schema 2는 show/summary에서 과거 미결속 기록으로 읽는다. 새 스키마의 mutator로 갱신하거나 출처를 추측해 이전하지 않는다. 미완료 과거 기록은 보존하고 새 run을 시작하도록 안내한다.
- schema 3 변경은 선택적 recorder에만 해당한다. 기록 불가 상태가 semantic READY/REVISE/BLOCKED를 바꾸지 않는다.

동일 run의 read-check-write는 실행별 OS 잠금 안에서 수행하고 최신 상태를 다시 검사한다. writer별 임시 파일과 원자 교체를 사용한다. finish/abandon 중 하나가 terminal 상태를 차지하면 다른 호출은 already-finished로 종료한다. outcome 재기록은 기존 계약대로 허용하되 잠금 순서로 직렬화한다. 잠금이 제공되지 않는 플랫폼에서는 일관된 오류를 반환하며 native 지원을 꾸며내지 않는다.

reader는 상태별 필수 필드·타입·timestamp·run ID 결속을 확인한다. 단일 잘못된 기록은 schema-invalid로, summary의 손상 기록은 정상 집계를 중단하지 않는 별도 수치로 보고한다. schema 2 과거 기록도 불완전한 JSON을 정상 기록으로 간주하지 않는다.

형식이 유효하지만 관찰이 모순되는 기록은 보존하고 anomaly로 표시한다. 정상 결과와 이상 관찰의 수치를 구분한다. recorder는 사용자가 기록한 semantic verdict를 자체 재판정하지 않는다.

## 7. 검증과 반례

| 영역 | 반드시 잡을 반례 | 유지할 정상 동작 |
| --- | --- | --- |
| CI | 공통 경로인데 repository-contract가 빠짐 | 제품 전용 변경의 좁은 선택 |
| Registry | 빈 단계, boolean schema, 추가 키 | 현재 네 제품의 정당한 등록 |
| Download | payload와 checksum을 함께 바꿈 | 동일 신뢰 원본의 standalone 설치 |
| Install | 같은 명령 재실행, 기존 디렉터리/다른/깨진 링크 | 첫 설치와 동일 링크의 무변경 성공 |
| Image | 같은 파일 별칭 출력, 손상 형식, 오염된 expected/candidate | 정상 형식 사실과 별도 시각 검사 |
| Korean | 의미 반전, 귀속 교환, 미언급 diagnose, 금지 실행 이벤트 | 양성 교정과 정상 파일 읽기 |
| How | 명시 깊이 무시, hop 불일치, 미결속 기록의 현재 검증 주장 | renderer 없는 완전한 채팅 출력 |
| Recorder | 같은 basename의 타 저장소, 동시 종료, 손상 파일 | 올바른 종료, 정상 집계, 과거 기록 열람 |

각 변경은 독립 반례가 기존 코드에서 실패함을 확인한 뒤 최소 수정한다. 승인된 계약 변화 때문에 기대값을 바꾸는 테스트는 해당 설계 절을 명시한다. 수정한 지시문의 특정 문구가 존재한다는 것만으로 행동을 검증했다고 하지 않는다.

제품 단위 검사 후 통합된 전체 profile과 windows-portable을 수행한다. portable 통과는 native Windows recorder 증거가 아니다. 추출 ZIP의 제품 검사와 변이 검증도 수행한다. 실제 모델·이미지 생성·배포는 포함하지 않는다.

## 8. 병렬 소유권과 통합 순서

각 제품 에이전트가 그 제품의 skills, tests/products, maintainer docs를 소유한다. 제품 README도 해당 에이전트가 수정하고 공유 설치 문서와 사실 단언의 변경 요청을 통합 담당에게 전달한다.

통합 담당은 scripts, products.toml, tests/repository, docs/users, CI를 소유한다. 같은 evidence.py 또는 live_matrix.py를 여러 writer가 동시에 고치지 않는다. 동시 슬롯은 제품 3개와 통합 1개를 쓰고 남은 제품은 다음 순서로 진행한다.

공통 검사·배포 계약과 네 제품의 수정은 독립 검토 후 합친다. 제품별 검사만 통과한 상태를 전체 완료로 보고하지 않는다. 새 실패·변경이 없으면 동일 전체 검증을 반복하지 않는다.

## 9. 이번 구현 범위 밖의 후보

- R6: 평가 모듈 물리적 추출, 중앙 문서 digest 구조 변경. 판정 입력이 확정된 뒤 실제 유지보수 필요가 입증되면 별도 제안한다. 규범·극성·추가 모순 검사를 제거하지 않는다.
- P5: 복합 위험을 focused reviewer의 명시적 집합으로 확장하거나 trigger를 배열로 바꾸는 정책. 현재 primary의 전체 검토 책임을 확인했으며 누락 실패는 재현되지 않았다.
- 실제 모델 품질, renderer별 시각·접근성 품질, native 신규 플랫폼 지원 측정.
- 범용 프레임워크, 저장소 분할, catalog 갱신, 실제 설치본 교체·삭제, 원격 게시.

이 문서 승인에 따라 writing-plans로 구현 순서·정확한 파일 범위·검증 명령을 계획한다. 현재 문서는 구현 완료 또는 의미 리뷰 READY의 증거가 아니다.
