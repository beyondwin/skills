# sddx 6.0.0 러너 신뢰성·관측성 설계 스펙

상태: 구현 전 설계. 이 문서는 현재 제품 계약을 변경하지 않는다.

기준: sddx `5.0.0`, 저장소 `main` `3c403a0`, 2026-09-24.
근거: 5.0.0·4.0.3 실전 런 로그 분석(Opus 2 + Grok 4.7 1), 변경 후보 적대 검토
(Opus 1 + Grok 4.7 1), 컨트롤러가 직접 확인한 원본 기록.
실행 문서: [구현 계획](../plans/2026-09-24-sddx-6.0.0.md).

## 1. 목표와 선택

실전 런에서 러너가 기록과 다른 일을 했다. 중단된 시도의 워커가 살아서 다음
시도와 같은 트리를 동시에 고쳤고(E1), Grok 워커의 도구 색인은 늘 비어
컨트롤러가 로그를 손으로 파싱했고(E2), 출력 없는 재개가 타임아웃까지
매달렸다(E3). 이번 개정은 **새 기계장치 없이 러너의 중단·대기 경로와 색인
파서를 고치고, 런에서 컨트롤러가 즉흥 대응한 규칙 몇 줄을 바로잡는다.**

| 대안 | 판단 |
| --- | --- |
| 문장 규칙만 추가 (워커 살려 두고 "겹쳐 띄우지 말라") | 겹침 금지는 이미 `dispatch.md`에 있는데도 E1이 났다. 러너 기록이 사실과 달라지는 문제는 남는다. 제외. |
| 감독 프로세스·프로세스 그룹 정리·자동 재시도 | 원인 미상 문제에 기계장치. 소유자가 원치 않는다. 제외. |
| 러너가 자기 직계 자식만 끝내고, 무출력 기한을 두고, 색인에 Grok 형태를 더한다 | 기존 `_end_process`·`timed_out`을 재사용한다. 채택. |

## 2. 근거 (원본 확인)

실전 런은 이 저장소 밖에 있다. 숫자는 이 문서 시점의 것이다.

- **E1 고아 워커.** won-sec-ai stage-1 T8-a의 `run.json`은 22:24:10Z
  `interrupted`, `exit_code: null`. 워커 로그와 `report.md`는 23:20Z까지 쓰였다.
  T8-b가 22:29–23:22Z에 같은 워크트리에서 돌았다. 컨트롤러는
  `pkill -f run_worker.py`로 러너만 죽였다. 러너는 설계상 자식을 남긴다
  (`run_worker.py:499-511`, `contract.md:324`, `dispatch.md:283-293`).
  근거였던 "Ctrl-C는 같은 그룹이라 워커에도 닿는다"는 러너에만 가는 SIGTERM에서
  성립하지 않는다. 재개에 살아 있는 자식은 필요 없다(T4 exit -15 뒤 T4-cont 재개 성공).
- **E2 빈 색인.** Grok `streaming-messages-json`에는 `"type":"tool_call"`이
  없다(T5-a 0/68, T8-b 0/220 `tool_use`). 호출은
  `assistant.message.content[]`의 `{type: tool_use, id, name, input}`, 결과는
  `user.message.content[]`의 `{type: tool_result, tool_use_id, content}`이고
  `content`는 JSON 문자열이다. `run_terminal_command` 결과는 정수 `exit_code`를
  갖거나(전경), 백그라운드면 `status`·`task_id`만 갖는다. grep 결과도
  `exit_code`를 가지므로 셸은 도구 이름으로만 가린다. 컨트롤러는 로그를 63–81회
  직접 파싱했다.
- **E3 무출력 재개.** T4-fix1b(1766초)와 T4-fix1c(3004초)는 이미 죽은 세션을
  재개했고 stdout 0바이트였다. 같은 일을 새 워커에 이어가기 브리프로 준
  T4-fix1-finish-a는 19분에 끝났다. 원인 미상(가설: 백그라운드 셸이 돌던 중
  죽은 세션의 재개가 init 전에 멈춘다. 표본 2건).
- **E4 잘못된 원인 문구.** 모든 러너 SIGTERM이 "the controller interrupted the
  attempt"로 기록돼, 하네스 kill을 컨트롤러 탓으로 읽고 감독 스크립트를 만들었다.
- **E5 제약 누락.** 4.0.3 런의 fix brief 9개 중 8개에 Global Constraints가
  없었다. `extract_task.py --heading "Global Constraints"`로 절만 뽑는 길은 이미
  있지만 문서에 없다.
- **E6 XHigh 모순.** 구현 XHigh 조건 "High already failed review on this task"
  (`SKILL.md:279`, `contract.md:118`)는 모든 fix 라운드를 XHigh·fresh로 만들어
  "라운드 1–3은 effort가 같을 때 재개"와 동시에 지킬 수 없다.
- **E7 기본 타임아웃.** 3600초. T2는 커밋 뒤 보고서를 쓰다 잘렸고, 정상 종료한
  큰 과제는 3100–4053초였다.
- **E8 보고 시점.** T2 재개는 약 11.7만 입력 토큰으로 상태를 복원했고 워크트리
  밖 Grok 세션 기록을 읽었다.
- **E9 대기·부모 폴더.** attempt 부모 폴더가 없어 첫 실행이 거부됐는데 `| tail`이
  exit를 가렸다. 컨트롤러는 러너 종료 뒤에도 쓰이던 `report.md`를 기다렸다.

## 3. Global Constraints

- 수정 대상은 `skills/sddx/`, `tests/products/sddx/`,
  `docs/maintainers/products/sddx/`, `tests/repository/test_release_contract.py`,
  이 스펙과 구현 계획이다. Superpowers 파일과 다른 제품은 고치지 않는다.
- Python 3.11 이상, 표준 라이브러리만. 새 런타임 의존성 없음.
- `run.json` 스키마(필드·`schema_version` 2·`state` 값 목록)는 바꾸지 않는다.
  새 state를 만들지 않는다.
- 워커 argv, resolver, sandbox 준비·정리는 바꾸지 않는다.
- 러너는 자기 **직계 자식 하나**에만 신호를 보낸다. 프로세스 그룹 신호, 손자
  추적, 감독 프로세스, 자동 재시도는 넣지 않는다.
- status 색인 한도(읽기 64, 검색 32, 셸 32, 명령 200자)와 64 KiB 응답 한도는
  그대로다. 파일 본문·stdout·stderr·thinking은 색인에 넣지 않는다.
- 픽스처는 합성이다. 실전 런의 원문·비공개 경로·자격 증명·receipt를 넣지 않는다.
- 지원 호스트 `claude-code`, `codex`, 지원 OS macOS는 그대로다.
- 제품 버전 `6.0.0`, 날짜 `2026-09-24`. 태그와 GitHub Release는 만들지 않는다.
- 테스트 명령은 저장소 루트에서 `PYTHONDONTWRITEBYTECODE=1`을 붙인다.

## 4. 변경

### R1. 중단 시 직계 자식을 끝낸다 (E1, E4)

`interrupted()`는 다음 순서를 따른다.

1. 즉시 `state: interrupted`, `exit_code: poll()`, `ended_at`, 새 `error`를 기록한다.
   두 번째 인터럽트가 와도 `running`으로 남지 않게 하기 위해서다.
2. 자식이 살아 있으면 `_end_process`(SIGTERM → 10초 → SIGKILL → 10초)로 끝낸다.
   이 대기 중 두 번째 `KeyboardInterrupt`가 오면 곧바로 `kill()`로 넘어간다.
   이미 사라진 자식에 대한 `ProcessLookupError`는 무시한다.
3. `exit_code`를 `poll()` 값으로 다시 기록한다(끝내지 못했으면 `null`).

`error`는 `the runner was interrupted (SIGTERM or Ctrl-C)`로 바꾼다. 보낸 주체를
주장하지 않는다. 래퍼 exit 130, 세션 ID 보존 규칙은 그대로다. 손자 프로세스는
여전히 쫓지 않으므로 "cleanup 전에 워커와 그 자식이 끝났는지 확인" 규칙은 남는다.

### R2. 첫 출력 기한 (E3)

새 시도와 재개 모두에 모듈 상수 `FIRST_OUTPUT_SECONDS = 300`을 둔다.
시작 후 300초 동안 stdout이 0바이트이면 러너는 `_end_process`로 자식을 끝내고
`state: timed_out`, 래퍼 exit 124, `error: the worker wrote no output within 300
seconds`를 기록한다. `--timeout 0`이어도 이 기한은 적용된다. `--timeout`이
300보다 짧으면 `--timeout`이 먼저다. CLI 플래그는 만들지 않는다.

두 백엔드 모두 첫 줄이 init 이벤트라 정상 시도는 수 초 안에 stdout이 생긴다.
init 뒤에 멈추는 경우는 이 기한 밖이며 `--timeout`이 잡는다.

컨트롤러 규칙: `error`가 이 무출력 문장이면 `--timeout`을 올려 다시 돌리지 않고,
그 세션을 재개하지도 않는다. 새 워커에 이어가기 브리프를 준다. 그 밖의 재개
규칙(`session_id_in_log`로 재개)은 그대로다.

검토에서 갈린 두 선택과 이유:

- **기록 상태.** Grok 검토는 `timed_out`이면 컨트롤러가 타임아웃을 올려 재시도할
  것이라며 `interrupted`를 권했다. 채택안은 `timed_out`이다. 러너가 시간 기준으로
  끝낸 것이 사실이고, `interrupted`는 E4처럼 "누군가 중단했다"는 틀린 사실을 적으며,
  새 state 값은 스키마 변경이다. 오독은 위의 컨트롤러 규칙과 구별되는 `error`
  문장으로 막는다.
- **적용 범위.** Grok 검토는 재개에만, Opus 검토는 모든 시도에 걸자고 했다. 채택안은
  모든 시도다. 정상 스트림의 첫 줄은 init이고, 한 규칙이 재개 특례보다 단순하다.
  Cursor의 첫 줄 시각은 측정하지 않았다(§8).

### R3. 기본 타임아웃 7200초 (E7)

`DEFAULT_TIMEOUT_SECONDS`를 7200으로 올린다. R2가 무출력 매달림을 5분에
끊으므로 긴 기본값의 비용은 init 뒤 정지에 한정된다.

### R4. Grok 도구 색인 (E2)

`read_tools_index`에 Grok 분기를 더한다. Cursor `tool_call` 분기는 그대로다.

- `assistant` 이벤트의 `message.content[]` 중 `type: tool_use`:
  - `read_file` → `reads`에 `input.target_file`(중복 제거).
  - `grep` → `searches`에 `{pattern: input.pattern, path: input.path}`.
  - `run_terminal_command` → `shells`에 `{exit_code: null, command:
    input.command[:200]}`을 넣고 `id`를 기억한다.
  - `list_dir` → `searches`에 `{pattern: null, path: input.target_directory}`.
    Search paths 규칙이 파일명 목록의 범위를 다루므로 역할 판정에 필요하다.
  - 그 밖의 이름(`search_replace`, `get_command_or_subagent_output` 등)은 건너뛴다.
- `user` 이벤트의 `message.content[]` 중 `type: tool_result`: `tool_use_id`가
  기억한 셸이면 `content`(문자열이면 JSON 파싱, 실패하면 무시)의 정수
  `exit_code`를 그 항목에 채운다. 본문은 읽기만 하고 복사하지 않는다.
- 셸의 `exit_code`는 Grok에서 `null`일 수 있다(백그라운드 셸, 결과 전 중단).
  Cursor 셸은 지금처럼 exit가 있는 완료 호출만 넣는다.
- 한도와 `truncated` 규칙은 공유한다.

### R5. fix brief의 제약 (E5) — 문서만

`dispatch.md` 3단계와 `contract.md`에 적는다. 계획 heading이 없는 brief(fix,
이어가기)는 `extract_task.py <plan> --heading "Global Constraints" --output
<file>`의 출력으로 시작한다. 계획이 다른 계획의 제약을 참조하면 그 계획에서
뽑는다. 손으로 옮기거나 `/tmp` 캐시를 쓰지 않는다. `extract_task.py`는 바꾸지
않는다.

### R6. XHigh 모순 삭제 (E6)

구현 XHigh 조건에서 "High already failed review on this task"(`SKILL.md:279`)와
한국어 면 "이 과제에서 High 리뷰가 이미 실패한 경우"(`contract.md:118`)를
지운다. 라운드 4–5 fresh XHigh 규칙이 반복 실패를 이미 다룬다. 리뷰어 표의
"a defect the reviews keep missing"은 그대로다.

### R7. 규칙 문장 (E8, E9, E1)

- 워커(`worker-prompt.md`): 커밋 직후, 추가 확인 전에 `report.md`를 먼저 쓰고
  확인 뒤 고친다. 백그라운드 명령의 결과는 공급자의 출력 도구
  (`get_command_or_subagent_output`)로 받고, 공급자 세션 디렉터리를 파일 읽기나
  검색으로 열지 않는다. 종료 코드를 모르면 모른다고 적는다. Search paths 문구
  자체는 바꾸지 않는다.
- `Host checks`: 과제 brief에 적힌 Host checks는 그 과제 리뷰 전에 돌린다.
- attempt 부모: 첫 실행 전 `worker-attempts/` 부모 폴더를 만든다. `run`·`status`
  출력을 `tail` 등으로 파이프해 exit를 가리지 않는다.
- 대기와 중지: 시도가 끝났다는 판단은 `state != running`이고 `pid_alive: false`다.
  이전 시도의 `pid_alive`가 true인 동안 새 시도를 띄우지 않는다. 워커를 멈출 때는
  기록된 러너 pid를 쓰고 `pkill -f`를 쓰지 않는다.

제외(증거 부족 또는 SDD 소유): BLOCKED 재파견의 라운드 상한 문장, CI 포맷 명령
의무화, 샌드박스 캐시 경로, 본문 중복 정리(별도 작업).

## 7. 검증

### 오프라인 (필수)

- `PYTHONDONTWRITEBYTECODE=1 python3 scripts/verify.py --skill sddx`, 머지 전
  `python3 scripts/verify.py`.
- R1: 한 번 인터럽트 뒤 자식이 끝나고 `exit_code`가 음수 정수, 두 번째 인터럽트에도

- R4: 합성 Grok fixture로 reads·searches·shells(exit 채움, 백그라운드 null),
  `list_dir` 경로, 비셸 도구의 `exit_code` 무시, 결과 본문 비복사, 한도·`truncated`. 기존 Cursor
  테스트는 그대로 통과.
- 과거 실전 로그에 대한 읽기 전용 확인(커밋하지 않음): 변경 후 `status`를
  won-sec-ai T4-cont에 돌려 목록이 채워지는지, Cursor 로그(teacher-style
  task-6c)에서 변경 전후 `tools`가 byte 단위로 같은지.

### 라이브 (macOS, 이번에 명시 승인됨)

`testing.md` "병합 전 라이브 재확인" 절차를 쓴다. 대상은 scratchpad의 새 git
저장소와 폐기용 linked worktree이고, 실제 Grok Build `grok-4.7` High다. 실전
프로젝트는 쓰지 않는다. receipt·로그는 커밋하지 않고 결과만 `testing.md`에 적는다.

| # | 시나리오 | 통과 기준 |
| --- | --- | --- |
| L1 | README 읽기, grep 한 번, `echo hi`, 파일 하나 커밋, report | `exited` 0, `stdout_bytes > 0`, `tools.reads`·`searches` 비어 있지 않음, `shells`에 `echo hi` exit 0, status에 README 본문 없음 |
| L2 | L1 세션을 `--resume`으로 한 줄 추가 | 수 초 안에 stdout 증가, 무출력 기한 미발동, 같은 `session_id`로 `exited` |
| L3 | `sleep 120`을 포함한 brief, `session_id`와 `pid_alive: true` 확인 뒤 러너 pid에만 `kill -TERM` | 15초 안에 워커가 `ps`에서 사라짐, `interrupted`, 음수 `exit_code`, 새 문장, 래퍼 130, `pid_alive: false`. 남은 `sleep` 손자는 있는 그대로 기록 |
| L4 | L3 세션을 `--resume` | 결과를 그대로 기록(멈추면 R2가 5분에 끊어야 함). E3 재현은 목표가 아니다 |
| L5 | `--timeout 45`와 `sleep 120` brief | `timed_out`, 래퍼 124, 워커 사망 |

각 시나리오 뒤 `prepare_grok_sandbox.py cleanup`이 `cleaned: true`여야 한다.
예상 비용은 약 30분, 수 달러 이내다. 워커가 저장소 밖으로 나가면 그 시도를 끝낸다.
라이브 통과는 이 Mac과 이 Grok 버전의 관측일 뿐이며 Cursor 경로는 오프라인 증거만
있다고 적는다.

## 8. 남는 것

- 손자 프로세스(Gradle 데몬, 백그라운드 셸)는 러너 밖이다.
- init 뒤 멈춤은 R2가 못 잡는다. Cursor 스트림의 첫 줄 시각은 측정하지 않았다.
- R1로 중단된 워커는 스스로 끝낼 기회 없이 SIGTERM을 받는다. 재개 가능성의 근거는
  T4(exit -15) 뒤 T4-cont 재개 성공 한 건이고, 라이브 L4가 다시 관측한다.
- E3 원인은 미상이다.
- `run.json`은 적용된 `--timeout` 값을 기록하지 않는다(이번 범위 밖).
